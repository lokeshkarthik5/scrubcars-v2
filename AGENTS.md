# Project: Detlio — agent instructions

## Stack

- **Framework**: Next.js (App Router)
- **Language**: TypeScript
- **Database**: PostgreSQL
- **ORM**: Drizzle ORM
- **Auth**: OTP (SMS) + Google OAuth, JWT access tokens + refresh tokens (HttpOnly cookies)
- **Payments**: Razorpay (online), cash on service
- **Storage**: Cloudflare R2 (S3 API, `lib/storage.ts`) for vendor, service and job photos; Cloudflare Stream (`lib/stream.ts`) for service videos. Photos go browser → R2 on a presigned URL, so the API never sees the bytes: every image upload re-encodes the file in the browser first (`stripImageMetadata`, `packages/core/src/image-upload.ts`) to drop EXIF/GPS. A new image upload path must do the same. Garage documents (ID, bank proof) are the exception to "public": a separate **private** bucket, `R2_DOCS_BUCKET` (`lib/document-storage.ts`), read only through 5-minute presigned links; see Garage documents (0043)

## Rules

### Repository layout

This is a bun-workspaces monorepo driven by Turborepo. Four deployables:

```
apps/users      detlio.com          customer app
apps/vendors    vendor.detlio.com   vendor portal
apps/admin      admin.detlio.com    operations panel
apps/server     api.detlio.com      Hono API
packages/core   @repo/core          API client, types, stores, domain helpers
packages/ui     @repo/ui            shared components + globals.css
```

- Each frontend serves its routes at their real public paths. There is no
  middleware rewriting `/vendor/*` or `/admin/*` any more — a route's directory
  under `app/` is the URL it is served at. Do not reintroduce a path map.
- Surface-specific code lives in its app. `packages/*` is for code at least two
  apps use; `packages/core` must never import from `packages/ui`.
- The three frontends call `api.detlio.com` directly. Any new origin that needs
  to reach the API must be added to `corsOrigin` in `apps/server/src/lib/env.ts`.
- `apps/server/src/package.json` is a one-line ESM marker required by the Vercel
  build output. It is not a workspace — never add `apps/server/**` to the
  workspace globs, and do not delete or rename it.

### Database

- Do NOT run migrations when making schema changes
- Do NOT call `drizzle-kit push` or `drizzle-kit migrate`
- Only modify schema files — the developer runs migrations manually
- Production is migrated by `.github/workflows/release-api.yml` after E2E passes on `main`, before the API deploys. A new migration file must:
  - take the next number with no gap (`0026_…` after `0025_…`) and have a matching entry in `drizzle/meta/_journal.json`
  - run inside a single transaction — no `BEGIN`/`COMMIT`, `CONCURRENTLY` or `VACUUM`; a new enum value cannot be used in the same file that adds it
  - be additive relative to the code currently in production; drops and renames go in a later release, once nothing reads the old shape

Request schemas are `.strict()` so nothing else can ride along. The one exception is the garage import below (owner decision, declared in the privacy policy's section 12): it sends the documents a garage gave us to join, never customers' data
- **AI text is a draft, never saved by the AI call**: `POST /admin/services/describe` only returns text for a form field, and every answer must pass `lib/copy-rules.ts` plus the description rules in `lib/service-description.ts` (1–2 plain sentences, at most 200 characters, no prices, no times unless given, no claims), with one retry; otherwise 422 `AI_NO_DESCRIPTION`. Any SDK error is 503 `AI_UNAVAILABLE`. Rate limited per admin per hour (`AI_DESCRIBE_RATE_LIMIT`, default 60)
- **Garage import** (`POST /admin/vendor-imports/extract`, `modules/vendor-imports`, rules in `lib/garage-import/`): photos and PDFs are read by `DocumentClient` (strict JSON-schema output, 50 s timeout, no retry — the API function's limit is 60 s in `vercel.json`); a Tally CSV is parsed by fixed rules with no AI (header → field table in `lib/garage-import/tally.ts`). The model only copies what is written; every decision is code: phones to 10 digits, "Call"/"on inspection" → On inspection with the fee missing, "from ₹X" → X to check, a missing duration is never guessed, the owner phone is always `check` (Create attaches the garage to whoever has that number — `POST /admin/vendor-imports/owner-account` says who). Drafts are held to the create endpoint's own zod schemas. **Files are never stored or logged** (memory for the one request; logs carry counts, sizes and timing only; every `responses.create` in `lib/ai.ts` sends `store: false`, or OpenAI keeps the response for 30 days), and **nothing is saved by the import**: the review screen creates the garage through the ordinary `POST /admin/vendors`, **always as Pending and not verified**. Errors: 503 `AI_UNAVAILABLE`, 422 `IMPORT_UNREADABLE`, 413 `IMPORT_TOO_LARGE`. Rate limited per admin per hour (`AI_IMPORT_RATE_LIMIT`, default 30)
- **Tests never call OpenAI**: unit tests pass a fake `TextClient` or `DocumentClient` (or, for the SDK client itself, a canned `fetch`); E2E runs with `AI_FAKE=1` (`.env.e2e`), which answers every request with `FAKE_AI_TEXT` and reads every photo or PDF as the same poster, `FAKE_GARAGE_READING` (`lib/garage-import/vision.ts`, asserted on by `specs/admin/garage-import.spec.ts`). The server refuses to boot with `AI_FAKE` set in production, like `E2E_FAKE_PAYMENTS`

### Module structure

Every feature module must follow this exact file structure:

```
module.route.ts        - route handlers
module.controller.ts   — request/response only, no business logic
module.service.ts      — business logic, orchestration
module.validation.ts   — zod schemas for request validation
module.repository.ts   — all DB queries via Drizzle ORM, no logic
```

- Controllers call services only
- Services call repositories only
- Repositories call the DB only — no business logic, no HTTP concerns
- Validation schemas live in `module.validation.ts` and are used in controllers before calling services

## Data model overview

### Auth tables

- `users` — single table for all user types. Flags: `is_customer`, `is_vendor_owner`. There is deliberately no `is_admin`: platform admin comes from a `super_admin` row in `user_member_mapping` or the env-credential break-glass login, never from a column or a JWT claim
- `user_member_mapping` — **the single role table for the whole product**: `(vendor_id, user_id, role, status)`. `role` is namespaced by scope — `user` / `super_admin` (both `vendor_id IS NULL`) and `vendor_admin` / `vendor_operator` (both `vendor_id NOT NULL`), enforced by a CHECK constraint. The absence of a row *is* the `user` role; baseline accounts are never materialized
- `otp_verifications` — stateless OTP log. `purpose`: `login` / `register` / `vendor_onboard`. `otp_code` holds a keyed hash of the code, never the code (`otpDigest` in `lib/otp.ts`: HMAC-SHA256 over purpose, phone and code, keyed from `JWT_SECRET`, cut to the column's 10 characters, compared with `otpMatches`). Each code sent deletes a batch of codes that expired over a day ago. Never log a code; the only print is `sendOtpSms`'s local-dev stand-in for the phone
- `refresh_tokens` — one row per session. Store SHA-256 hash of raw token, never plaintext

### Customer tables

- `user_addresses` — saved addresses with `lat/lng`. Doorstep location is snapshotted onto `bookings` at booking time
- `user_vehicles` — saved car profiles. `is_default` for auto-selection. `wash_interval_days` (0031) is the customer's wash reminder interval for Home's wash bar: 7/10/14/21/30 only (CHECK), null = the default, 14 days or 10 from 1 Oct to 31 Dec in IST (`lib/wash-status.ts`, Chennai-only and hard-coded). Set with `PATCH /users/me/vehicles/:id { washIntervalDays }`. Each car has a history page and coating/detailing follow-ups (`vehicle_service_reminders`, 0046; see Car history and service reminders)
- `users.updates_seen_at` (0031) — when the customer last opened Updates; anything after it is unread and lights Home's bell (null reads as `users.created_at`). `POST /users/me/updates/seen` only ever moves it forward, and never past the server's clock. 0031 set it to now for every existing account

### Vendor tables

- `vendors` — the company. `owner_id` names the one person who owns the business; `user_member_mapping` answers the separate question of who can use the portal and with what power. `is_verified` is flipped manually by admin. `slot_interval_mins` sets calendar granularity (30/45/60). `owner_id` cascades from `users`, so `DELETE /users/me` refuses an account that owns a garage (409 `VENDOR_OWNER_ACCOUNT`, `lib/account-deletion.ts`) rather than delete the garage and its bookings with it
- **Live** (customers can find the garage) is `status = 'active'` AND `is_verified` AND not paused (`bookings_paused_at IS NULL`) AND not in the Bin (`deleted_at IS NULL`, see The garage Bin). One definition: `LISTED_TO_CUSTOMERS` (SQL, alias `v`) and its twin `isListedToCustomers` in `modules/vendors/vendors.predicates.ts`, pinned together by its test. The customer lists and Home's Nearby run the SQL; the admin list's `live` flag is the twin. Change one, change both — never restate the conditions. **Active** is only the stage (approved by Detlio), and includes paused and unverified garages
- **Readiness** — the admin garage list's "what's missing" checklist, `lib/vendor-readiness.ts` (pure, unit-tested), returned per garage on `GET /admin/vendors` as `readiness` items `{ key, severity, label, detail?, short, tab }`, where `tab` is the edit page's `?tab=` that fixes it. **Blocking** (customers can't book it): no active plain services; neither drop-in nor doorstep on; no open day (no `vendor_working_hours` rows, or all closed). **Fix**: no pin, or pin not confirmed; services without a description (counted); `vehicle_types` empty or holding a retired label (compared case- and space-insensitively — seeds store `hatchback`/`suv`); bays null or 0. **Optional**: no logo; no photos; doorstep on with no radius and no drawn area (the 10 km default is used — owner decision); documents not verified (0043, `tab: 'documents'`, only while garage documents are on; never blocking). Only blocking and fix count as needing fixing. Not checked on purpose: distance from Chennai (garages in other towns are allowed), verification (that is the Verify button). Packages are left out of the services rules. `GET /admin/vendors` stays one full array (other screens' garage pickers read it); the panel's chips (`apps/admin/lib/vendor-list.ts`: All · Live · Active · Pending · Suspended · Archived · Bin, `?show=`, default Live) filter and count it on the client; a garage in the Bin is under Bin and in no other chip or count, and the Bookings garage filter leaves it out. Any admin write that changes what the list shows must invalidate `adminVendorKeys.lists()` (`useInvalidateAdminVendors`), since verify/archive/restore return the bare row without `live` or `readiness`
- `vendor_working_hours` — one row per day of week (0=Sun … 6=Sat). `is_closed` handles off days
- `vendor_service_areas` — pincodes/areas covered for doorstep jobs
- `vendor_photos` — ordered gallery. `sort_order` controls display sequence

### Catalog

- `services` — vendor-scoped. `category`: `car_wash` / `detailing` / `coating` / `scratch_removal` / `others` / `package`. `duration_mins` drives slot consumption
- `service_package_items` — composition of a package. A package is a `services` row with `category = 'package'` that bundles other services of the same vendor, so it books, prices and consumes slots exactly like a service and `bookings.service_id` stays a single FK. Its price and duration are vendor-set and independent of its members; the members exist to itemize contents and compute savings from their live prices
  - Listings that mean "plain services" MUST exclude `category = 'package'` (see `listServices`, and the admin repository — `listActiveServiceIds` especially, since the admin editor reconciles against it)
  - The booking path MUST NOT exclude packages — a package occupies a slot like any other service
  - Packages are created only via `/vendors/me/packages`; `POST /vendors/me/services` rejects `category: 'package'` because a package with no members is invalid
  - The admin editor's save sends the garage's full list and the server hides any live service missing from it, so the editor must never leave a typed-in row out: a row that is not ready blocks the save instead (`apps/admin/lib/service-rows.ts`). It sends `services` only when the Services tab has changes (`apps/admin/lib/garage-edit.ts` `dirtyTabs`). "How customers book" (`dropinEnabled` / `doorstepEnabled` / `doorstepRadiusKm`) is saved on tap by its own card above the tabs and is never part of Save changes, so the two can't overwrite each other. Ready-made services are `packages/core/src/service-templates.ts`; their descriptions pass the copy rules (tested on both sides). Admin hides and shows services one at a time with `PATCH /admin/vendors/:id/services/:serviceId/active` (plain services only; 409 `SERVICE_IN_PACKAGE` for one inside a package) and lists hidden ones at `GET /admin/vendors/:id/services/hidden`
- Category labels live in `apps/server/src/lib/categories.ts` and `packages/core/src/categories.ts`, both keyed exhaustively on the category union — add new categories there or the build fails

### Service photos and videos (0033)

- `service_images` holds a service's (or package's) photos **and** its video: `kind` `image`/`video`, `source` `upload`/`ai` (text + CHECK). At most `R2_MAX_IMAGES_PER_SERVICE` (3) photos and **one** video, checked in `serviceMediaService` (`modules/service-media`) by `insertMediaUnderLimit` under a per-service `pg_advisory_xact_lock('service-media:<id>')`, taken on its own and never alongside the booking-write locks (outside their order, like job photos'). Pure rules in `lib/service-media.ts`; garage photo routes stay `/vendors/me/services/:id/images…` (vendor_admin, `resolveTenant`) and admin's `/admin/services/:serviceId/images…`, both calling the shared service
- **The privacy tick**: every upload (photo or video, garage or admin) needs `consent: true` — "no number plates or faces can be read, or the owner agreed" — else 400 `MEDIA_CONSENT_REQUIRED`; `consent_confirmed_at` records it, `uploaded_by` names the admin or `'garage'`. A photo URL must sit in its own service's folder (`vendors/<vendorId>/services/<serviceId>/`)
- **Video** goes through Cloudflare Stream (`lib/stream.ts`, plain fetch, no SDK): a direct creator upload ≤ 200 MB or a tus upload above, `maxDurationSeconds` 60. The row is `video_status = 'processing'` until `POST /api/v1/webhooks/cloudflare-stream` (signed: `Webhook-Signature`, HMAC-SHA256 of `time.body`, 5 min tolerance) or the upload block's poll (`GET …/media/:mediaId`, which asks Stream) settles it to `ready` (`duration_secs`, `poster_url`) or `error` (`video_error`, plain words, never Stream's text); `settleVideo` only moves a processing row. **Replacing never loses the old video**: a ready video stays (customers keep seeing it) while its replacement uploads and processes, and is deleted only by `settleVideo` when the new one is ready, in the same transaction and lock (AI samples likewise go only then); if the new one fails or is removed, the old one stays. So a service may briefly hold a ready video plus one not-ready replacement, never more (`videoCountsOnStart`, `removedOnVideoStart`, `removedWhenVideoReady`). Off — slot hidden, routes 404 — unless all four `CLOUDFLARE_*` env vars are set. Removing or replacing deletes the Stream video (and a photo's R2 object) after the commit, best effort (`removeMediaFiles`)
- **AI sample pictures** (admin only, `OPENAI_API_KEY`, else `GET /admin/ai/config` → `pictures: false` and 404s; in the admin editor it is in each saved service's ⋯, "Photos and video"): two options from the official `openai` SDK (`AI_IMAGE_MODEL`), parked under `ai-temp/<serviceId>/` in R2 (a 1-day lifecycle rule clears leftovers), the chosen one copied into the service's folder as `source = 'ai'`. Only while the service has no real photo or video; a real photo, or a video once ready, removes the AI samples in the same transaction. The prompt is the admin's text cleaned of emails, phone numbers and plates, plus a fixed style — never personal data
- **Customers** get `toPublicMedia`: photos and *ready* videos only, `kind`/`url`/`posterUrl`/`durationSecs`/`source` — never `consent_confirmed_at`, `uploaded_by`, status or uid. Anything AI-made or drawn (the `packages/ui` sample art, chosen by `sampleArtFor`) is tagged "Sample"/"Sample image"; garage uploads "From <garage>". Videos play on tap only (`preload="none"`, hls.js loaded on the first Play)
- **Tests never call Cloudflare or OpenAI**: `STREAM_FAKE=1` (uploads land on `/api/v1/fake-stream`; `apps/e2e/support/stream.ts` fires the signed webhook) and `AI_FAKE=1` (a fixed PNG). Both are refused at boot in production, like `E2E_FAKE_PAYMENTS`. Setup for production: `apps/server/docs/service-media.md`

### The garage Bin (0034)

- **Archive and the Bin are different things** (owner decision, 16 Oct 2026). Archive (`status = 'archived'`) only hides a garage from customers; everything else carries on. The Bin is for garages being deleted: `vendors.deleted_at` set (with `deleted_by_name`, the typed name, and `deleted_reason`), stage, verification and pause left untouched so Restore brings back exactly what was there. Nothing in the Bin is deleted on its own
- **One rule, everywhere**: in the Bin is `deleted_at IS NOT NULL`, read only through `modules/vendors/vendors.predicates.ts` (`NOT_IN_BIN` for raw SQL over `vendors v`, `vendorNotInBin()` for Drizzle, `isInBin` for a row, `vendorPageOpen(id)` for the garage page's lookup). It is part of `LISTED_TO_CUSTOMERS` / `isListedToCustomers`, and every customer read that skips the list (garage page, services, packages, slots, hours, holidays, public reviews, checkout, `checkGarageCanTake`, `garageRefusalForBooking`, Book again, offers) must say it too. A new customer read of a garage that does not go through these is a bug
- **Its team is locked out**: every seat read in `members.repository` joins `vendors` and requires `vendorNotInBin()` beside the seat's own `status = 'active'` (two filters on two tables; neither stands in for the other). `resolveTenant`'s super_admin support path 404s a garage in the Bin, or one that does not exist, before it writes the access record. Seat rows are kept, so Restore gives access back as it was. Moving to the Bin, restoring and deleting forever re-sync every seat holder's `is_vendor_owner` in the same transaction (the vendor-app login is "active seat or the flag"), so someone who also has a live garage keeps their login and someone who does not loses it
- **Admin**: `modules/vendor-bin` (super-admin; `GET /admin/vendors/:id/bin-preview`, `POST …/bin { actorName, reason? }`, `POST …/restore { actorName }`, `GET …/delete-preview`, `DELETE /admin/vendors/:id { actorName, confirmName, selectionHash }`). Every action writes `admin_audit_log` (`garage_binned`, `garage_restored`, `garage_deleted`) with the typed name, and locks the garage row FOR UPDATE first. Any other admin write on a garage in the Bin is 409 `VENDOR_IN_BIN` (`assertWritableVendor` in admin.service, `resolveService` for admin media); reads still work, and the edit page opens read-only. Admin pickers (discounts, notices, the Bookings filter, demand/supply) leave the Bin out
- **Moving to the Bin with bookings to come is allowed**: each pending, confirmed or in-progress booking is cancelled after the commit through the admin cancel (`adminService.cancelBooking`, Detlio's own decision, reason "Garage removed"), so a paid one is a refund owed by `lib/refunds.ts` like any Detlio cancellation: refunded from the Refunds page, or by the automatic mode when `AUTO_REFUNDS` is on (the Bin itself never calls Razorpay). One that can't be cancelled (changed meanwhile) is listed in the answer
- **Delete forever** is only for a garage in the Bin (409 `VENDOR_NOT_IN_BIN`), with its name typed (400 `CONFIRM_NAME_MISMATCH`) and the preview's `selectionHash` (409 `PREVIEW_STALE`). It is the test-data reset's planner and deletes with the `garage` scope (every chain and every checkout of the garage, whenever made; `deletePlannedRows`, `finishRestarts`), so money classes, the receipt plan and the lock order are the reset's. Razorpay is never asked from here: null-mode money counts as unconfirmed and is kept (the reset's dry run records modes first). Then `lib/vendor-bin.ts` `purgeOutcome`: nothing kept → the garage row is deleted, in this order because of the RESTRICT diamond (package items, the plan's checkouts and bookings, services nothing points at, then the garage, whose cascade takes notices, garage-only offers and support-access rows; their counts go in the audit row); something kept → a tombstone (`purged_at`; business name, address, city, pincode and owner kept for receipts; phone, email, WhatsApp, maps link, logo and notes cleared; gallery, service media, package items, hours, closures, areas and seats deleted; services a kept booking names stay, off sale; garage-only offers switched off); over the reset's per-run cap → `partial`, the oldest deleted and the garage left in the Bin. A tombstone is in no admin list and its detail is a 404. R2 files (logo, gallery, service photos and AI pictures, job photos of deleted bookings, and garage documents from the private bucket — all but the signed agreement on a tombstone, 0043) and Stream videos go after the commit, best effort; Telegram gets "Garage deleted by <name>: <garage>, N bookings"
- `countOwnedVendors` (the cap on companies) counts a garage in the Bin but not a tombstone

### Complaints (0035)

- `complaints` — a customer's complaint with its number and clock (owner decision, 17 Oct 2026). Raised by a signed-in customer from a booking's Help sheet (booking and garage attached; the booking must be their own, anyone else's is a 404) or from the Contact page (neither): `POST`/`GET /users/me/complaints`, `modules/complaints`. The user id is always the session's; the schema is `.strict()`
- **The number** is `C-` and six digits (`formatComplaintNumber`), from `complaint_number_seq`: a SEQUENCE on purpose, so customers never wait on each other; a rolled-back insert leaves a gap. Not like receipt numbers, which must be gapless
- **The clock**: acknowledge within 24 hours, resolve within 7 days of `received_at` (0039; see below). The numbers live in `packages/core/src/complaints.ts`, which the legal pages (`GRIEVANCE_TIMELINES`), the customer app and admin read; `apps/server/src/lib/complaints.ts` is its twin (parity test). Overdue = open past acknowledge-by, or open/acknowledged past resolve-by (`complaintOverdue`); the admin list's SQL uses `overdueCutoffs`, never restated hours
- Status `open → acknowledged → resolved`, or `closed` (from any but closed; nothing reopens). Resolve needs `resolution_note`, which the customer reads; resolving or closing an open one stamps `acknowledged_at` then. `admin_note` never leaves admin. Moves are conditional updates (`COMPLAINT_ACTION_FROM`); a stale press is 409 `COMPLAINT_STATUS_CHANGED`. CHECKs in 0035 tie each status to its timestamps
- Every FK (`user_id`, `booking_id`, `vendor_id`) is `ON DELETE SET NULL`, and name, phone, booking reference and garage name are snapshotted, so `DELETE /users/me`, the reset and Delete forever keep the complaint
- Limits per customer (`complaintSubmitRefusal`): 5 open or acknowledged (409 `COMPLAINT_LIMIT_OPEN`), 3 an hour (429 `COMPLAINT_RATE_LIMIT`), counted under a per-customer advisory lock (`complaints:<userId>`) taken on its own, never alongside the booking-write locks
- A new complaint alerts ops on Telegram (`complaint_received`, Production only, the customer's words through `quoted()`). Start pilot clean takes a cutoff run's complaints as one row with one tick (`only.complaints`)
- **Logged complaints (0039)**: the team logs one that came by phone, WhatsApp, email or in person (`POST /admin/complaints`, super-admin, `.strict()`; rules in `modules/complaints/complaints.logging.ts`, pure). `source` (text + CHECK: `app` / `phone` / `whatsapp` / `email` / `in_person` / `other`; the API never accepts `app` from admin), `logged_by` (the typed name; null exactly when `app`). The phone finds the account (`users.phone`, ten digits) and links the complaint to it, under the account's name, so it is in their My complaints; no account → the typed name is required and kept with the phone. A booking reference must be the account's own booking (409 `COMPLAINT_BOOKING_NOT_THEIRS`). No per-customer limits for the team. Telegram says "By phone, logged by <name>."
- **The clock runs from `received_at` (0039)**, never `created_at`: the moment an app complaint was made, or the time the team gave, up to 7 days back (`resolveReceivedAt`; the insert takes `least(given, now())` because a CHECK keeps `received_at <= created_at`). Due times, Overdue (`overdueCutoffs` → `openReceivedBefore` / `unfinishedReceivedBefore`), the admin order and My complaints' date read it; the per-hour limit and the reset's cutoff still read `created_at`
- **Answers in Updates**: acknowledged / resolved / closed each add an Updates row (`complaint_acknowledged` / `complaint_resolved` / `complaint_closed`, `lib/home-updates.ts`, opening `/profile#my-complaints`); resolving or closing an open one is one row. A complaint resolved in the last 7 days and unread in Updates is Home's soft card (`complaint_resolved`) only when the place is free: `softCardWithComplaint` keeps a must-act card or Rate your wash. Never under To do. Only times and whether there is an answer are read (`homeRepository.listAnsweredComplaints`), never the team's note

### Refunds through Razorpay (0036)

- **Refund now** (`POST /admin/refunds/send { kind, id, amount?, expectedRefunded?, note? }`, super-admin, `.strict()`) sends a refund through Razorpay (`lib/razorpay.ts` `createRazorpayRefund`: `POST /v1/payments/:id/refund`, speed `normal` only — instant costs extra — amount in paise, notes `detlio_kind`/`detlio_id`/`detlio_source` plus `booking_id`/`intent_id`/`charge_id`, `X-Refund-Idempotency` from `refundIdempotencyKey`) and records it exactly like Mark refunded (`refund_ref`, `refunded_by` the admin, `refund_note` "Sent through Razorpay from the app by …"). Amount defaults to everything owed, may be lower, never higher. Mark refunded stays for refunds done in the dashboard
- **Never twice, never more than paid.** Every send, under the payment's lock, first reads `GET /v1/payments/:id/refunds` and records any refund we have no record of (`source = 'razorpay'`, or ours by its notes when an answer was lost) and settles our pending ones Razorpay has finished; a found refund that doesn't fit what is owed stops it (409 `REFUND_RAZORPAY_MISMATCH`, alert). Only then is what is still owed (`lib/refunds.ts`) sent. If Razorpay can't be read, nothing is sent (503). A sheet whose figures moved sends nothing (409 `REFUND_STATE_CHANGED`)
- **The refund lock**: `pg_advisory_xact_lock('refund:<Razorpay payment id>')` (or `refund:<kind>:<id>` without one), `refundsRepository.withRefundLock`, held across the Razorpay calls, by Refund now, Mark refunded, the automatic mode and the refund webhooks. Taken on its own, never alongside the booking-write locks; the automatic mode then takes `auto-refunds:cap`; the money row's own lock comes last at the write. The button and the automatic mode try-lock (409 `REFUND_BUSY` / skip); the webhook waits. With one DB connection, everything inside goes through the `tx` (`Conn`); a query on `db` there would deadlock
- **`refund_records` (0036)**: `source` (`recorded` / `razorpay` / `admin` / `auto`), `gateway_status` (`pending` / `processed` / `failed`, null = never asked), `settled_at`, `failure_reason`. A refund Razorpay refused outright is a `failed` row with no refund id. `refund.failed` (or a check finding it failed) marks the row failed, takes it off the money row's total (a full refund's payment goes back to `paid`, the row describes the latest standing refund again), notes the booking and alerts: the money is owed again. The one-per-starting-total index leaves failed rows out. **Every reader of the history excludes failed rows** (`STANDING_REFUND`; the receipt, Home/Updates). `refund.processed` marks it processed. The webhook only touches refunds recorded here; it routes `refund.*` before any payment handling
- **Automatic mode** (`AUTO_REFUNDS=on`, default off; while off nothing runs and nothing is read). `refundsService.queueAutoRefund` after the cancel commits (customer cancel, garage decline, admin cancel incl. the Bin, garage no-show, `settlePayment`'s refusal, `failIntent`, the cron's not-accepted-in-time cancel (0042)), via `runInBackground`; plus `sweepAutoRefunds` in the pending-digest cron (20 a run, 15 s budget, stops at the cap or when Razorpay is down). Rules in `lib/refund-sending.ts` `autoRefundHold`: never `bill`, never when anything was already refunded (no part amounts), never with an open/acknowledged complaint, only clear-cut causes (`autoRefundCause`), owed within the last 3 days, at most 3 failed tries. Daily cap `AUTO_REFUND_DAILY_CAP_INR` (default 20000, IST day, counted from `source = 'auto'` standing rows): the first refund that would pass it writes `auto_refund_cap_days` and alerts once; no more automatic refunds that day
- `E2E_FAKE_PAYMENTS` mints `rfnd_e2e_…` refunds in memory (same key, same refund; listable per payment), status `pending`
- Telegram: `refund_sent` (one per refund, auto/admin), `refund_failed` (one per failure), `auto_refund_cap_reached`. Customer: while an app-sent refund is pending, `refund.started` makes the booking page say "Refund of ₹X started on <date>. It reaches your account in 5–7 working days." (`customerRefundLine`)

### Suggested times and extra work (0041)

- **Suggest another time** (owner decision, 17 Oct 2026; `modules/time-proposals`, rules in `lib/time-proposals.ts`, pure): on a **pending, paid** booking the garage offers 1–3 of its own free times for the same job instead of declining. - **Extra work** (`lib/extra-work.ts`, pure): a `booking_charges` row of kind `extra_work` (one line: what and price; `paid_before` 0; up to 3 `photos` in the job-photos folder, uploaded like job photos and re-encoded in the browser). Paid with the final bill's `pay` / `verify` and webhook path (`settleCaptured`, conditional on `due` and its own order) — **paying is the approval**; the customer can decline, the garage withdraw while unpaid (`cancel_reason` `declined` / `withdrawn`). **Mark completed and Delivered are refused while one waits** (409 `EXTRA_WORK_AWAITING`, in the write too: `noOpenExtraWork`), so nothing lapses and nobody pays for a finished job. - **Money**: paid extra work is **kept only if the booking completes**; on any other end — cancelled by anyone, moved, a no-show on either side (a customer no-show included: the work was not done) — it is owed back (`isBillRefundable`, refund kind `bill`, never automatic). Receipts list it (`extraWork`, refunds `against: 'extra_work'`); commission charges it at the booking's main service rate and payouts include it, exactly as a paid final bill (`billsPaid` is every paid charge on the chain); Statistics' collected includes it
- **Home**: must-act order is suggested times, then extra work, then a bill, then a closed day (`pickActionCards`), still one card; Updates rows `time_proposal`, `extra_work_due` / `_paid` / `_declined` / `_withdrawn`. Telegram: `time_proposal_made`, `time_proposal_outcome`, `extra_work_paid`, `extra_work_declined`. No new analytics events

### Slot alerts: "Notify me if a slot opens" (0047)

- **The ask** (idea #18): at checkout, under the slot picker's times, a day that is all booked offers "Notify me if a slot opens"; a day with times left offers it as a quiet line for the parts of the day that have none. A part of the day is a window (`slot_alerts.time_window`, text + CHECK): Any time, Morning 06–12, Afternoon 12–17, Evening 17–22, by the slot's IST start, start included (`lib/slot-alerts.ts`, pure, unit-tested; words and numbers twinned in `packages/core/src/slot-alerts.ts`, `slot-alerts.parity.test.ts`). Signed-in customers only (`/users/me/slot-alerts`, `modules/slot-alerts`, the session's id, `.strict()`; anyone else's alert is a 404). Shown nowhere on a day that cannot open up (closed, paused, the job longer than the day) or with nothing booked (no time left to give notice for)
- **`slot_alerts`**: customer, garage, IST `date`, `time_window`, `booking_type`, `duration_mins` (the services' total, as the slot list adds them), `service_ids` (for the link only; no FK), `expires_at` = the end of `date` in IST, `notified_at` + `notified_slot_at` (both or neither, CHECK), `last_checked_at` (the sweep). Cascades with the customer and the garage. **Waiting** = not notified and `expires_at` ahead. **One waiting per customer, garage and date** (partial unique index): setting it again changes that one. **At most 5 waiting per customer** (`MAX_ACTIVE_SLOT_ALERTS`, 409 `SLOT_ALERT_LIMIT`), counted under `pg_advisory_xact_lock('slot-alerts:<userId>')`, taken on its own. Today up to 60 days ahead. **Refused when it makes no sense** (`askRefusal`, the slot rule run for the alert's job): a time free in the window now (409 `SLOT_ALERT_SLOT_FREE`: book it), a closed or paused day, a job too long for the day, or no time left in the window to give notice for (409 `SLOT_ALERT_NO_TIMES`); a booking type the garage does not take (409 `BOOKING_TYPE_NOT_OFFERED`)
- **Matching uses the slot list's own rule**: `slotsForDay` in `lib/slots.ts` (the day, hours and job length, the notice for the booking type, bays and the day's cap), which `jobSlots` (the picker, "Suggest another time") now runs too; then the window. The facts are read once per garage-day (`readDay`: hours, holiday, `listCapacityHolders`) and every waiting alert there is judged on them
- **What re-checks**: every write that frees capacity calls `slotAlertsService.capacityFreed(booking, reason)` after it commits (customer cancel, garage decline, admin cancel incl. the Bin's, a no-show recorded, the 0042 auto-cancel, a 0041 suggestion declined or expired, a customer move or a suggested time picked — the old time), `dayChanged` (a holiday removed) or `garageChanged` (pause lifted by the garage or admin, hours or slot length changed, admin's garage save, unarchive: every date with alerts waiting, 30 at most). All run in `runInBackground` and never slow or fail the write; with nothing waiting they cost one indexed read. A booking past midnight frees the next day too (`datesHeld`). **Any new path that cancels or moves a booking, or reopens a day, must call one of these.** Safety net: the pending-digest cron's `slotAlertsService.sweep` (garage-days unchecked longest first, 20 a run, 10 s budget), which also deletes alerts whose day ended over 31 days ago (1,000 a run)
- **Telling**: each alert with a free time in its window is **claimed** (`notified_at`, conditional on still waiting, so two re-checks tell it once), then a push (`customerSlotOpened` in `lib/push-messages.ts`, category `booking_update`, so the Booking updates switch; urgent; TTL until the time) and the Updates row (`slot_opened`, derived from `notified_at`, no event table). Words (`slotOpenedWords`): "A slot opened at <garage>", "Sat 24 Oct — 10:30 AM. Book before it goes." Both open checkout with the same services, the date and the mode (`slotAlertPath`: `/book/<garage>?service=…&date=…&mode=…`; checkout's `?date=` opens the picker on that day, `SlotPicker` `initialDate`). **First come: nothing is held**; every waiting alert that matches is told. A garage customers can no longer open, or that stopped taking that booking type, tells nobody
- **Apps**: checkout (`components/slot-alerts/slot-alert-ask.tsx`, through `SlotPicker`'s `renderDayExtra`), the garage page's "Waiting for a slot" card with Stop waiting, Profile → Slot alerts (`/profile/slot-alerts`, linked while any wait). No garage-facing change; no analytics events (0040's CHECK); the Home read gains one bounded query (`listToldSince`, 20 rows)
- E2E fixtures for this feature use ids `id(2700)`–`id(2799)` and phones `90000027xx` only (`seedSlotAlertRows`, `VENDORS.slotAlerts`, `CUSTOMERS.slotAlert`, `CUSTOMERS.slotAlertOther`, `CUSTOMERS.slotHolder`, `STAFF.slotAlertsOwner`, `BOOKINGS.slotAlertsHeld`)

### Car history and service reminders (0046)

- **A car's history** (idea #13; `GET /users/me/vehicles/:vehicleId/history[?category=]`, `modules/car-history`, rules in `lib/car-history.ts`, pure): every completed job on one of the customer's **current** cars (anyone else's, or an archived one, is 404 `VEHICLE_NOT_FOUND`), newest first, **one entry per reschedule chain** (its latest row: highest `reschedule_count`, then newest; the booking page, receipt and photos hang on it). Cancelled chains (no-shows included) are left out and only counted (`cancelledCount`; the page points to My bookings); jobs to come are not history. **Amount paid** = the latest row's payment (paid / collected / refunded; Razorpay's part plus any Detlio credit part not given back, 0049, as Statistics reads it) less its `refunded_amount`, plus paid `booking_charges` (final bill, extra work) less theirs; never the moved row's copy. Totals (washes and spend this IST year, and all time) are over what the filter shows; a package's members' categories count for the filter (`categoriesOf`). Calendar months from the IST completion date, clamped (`addMonths`). One row per job per kind (unique), so writing twice does nothing; the cron's catch-up writes any completion of the last 2 days that has none. A newer job of the same kind **supersedes** the older open ones; a booking for the car with a category in `FULFILLED_BY`, dated no earlier than 30 days before the due date, **answers** one: while paid and to come it is `booked` (nothing shown or sent), once completed `done` (persisted on completion, and read the same way on every read, so a missed write never shows a stale one). A cancelled booking answers nothing. Status `open` → `dismissed` / `done` / `superseded` once (`closed_at` CHECK); a removed car's reminders stay and are not shown
- **Customer actions**: `POST /users/me/service-reminders/:id/dismiss` (idempotent) and `/snooze` (due again 14 days from today, IST; 409 `REMINDER_CLOSED` once closed); another customer's is 404 `REMINDER_NOT_FOUND`. "Book" goes to `/search?category=<car_wash|coating|detailing>` with the car remembered for checkout; booking it is what marks it done (no reminder id rides on the booking)
- **Where it shows**: the car's page always shows the nearest open one (else the nearest booked one). Home's **soft card** `service_reminder` from 7 days before it is due until 60 days overdue, **only when the place is free**: no must-act card, no Rate your wash, no resolved complaint (`softCardWithReminder`); otherwise Updates only. Never under To do. Updates row `service_reminder` dated 09:00 IST on the due date in force (id `service_reminder:<id>:<dueOn>`, so a snooze makes a new unread row), opening the car's page; the Home read adds one query (two when there are reminders)
- **Push**: in the pending-digest cron's 09:00–09:59 IST runs (`carHistoryService.sweep`, quiet hours don't apply), one `customerServiceReminder` per open reminder whose due date in force is today, to customers with Reminders on and a device, **claimed by `notified_on`** (conditional update) before sending, so overlapping runs never send twice and a snooze earns one more on its own date. Booked or answered ones are skipped. Words: the reminder's name, "N months since your coating at <garage>". **Never the car** (make, model or plate). 50 a run, 10-second budget; nothing read while push is off
- `vehicle_service_reminders` cascades with the user, the car and the source booking (so `DELETE /users/me`, the reset and Delete forever take them); `done_booking_id` is SET NULL. Nothing here touches bookings, payments or receipts

### Garage response deadline (0042)

- **The rule** (owner decision, 17 Oct 2026; pure in `lib/response-deadline.ts`, unit-tested): a garage has `GARAGE_RESPONSE_MINUTES` (default 30, whole minutes 5–240) **of its opening hours** to accept, reject or suggest other times for a paid booking. Paid while open: payment + 30, the clock stopping at closing and running on at the next opening (paid 10 minutes before closing = 10 tonight + 20 tomorrow). Paid while shut (outside that IST day's `vendor_working_hours`, no hours row, `is_closed`, hours that don't run forwards, a `vendor_closures` holiday, or paused — a pause has no next opening): 30 minutes after it next opens. **Never later than 1 hour before the slot** (`SLOT_MARGIN_MS`); if that would leave under 15 minutes from payment, **15 minutes from payment (the floor, `RESPONSE_FLOOR_MS`)**, never past the slot's start. The floor only lifts the margin; it never lengthens a window the opening hours set
- `bookings.respond_by` is written **in the transaction that makes a booking paid and pending**: `consumeIntent` (from the payment), `settlePayment` (a pay-later booking paid now, if still pending) and a customer's `rescheduleBookingWithPayment` back to pending with a paid payment (a fresh deadline from the move). Each calls `respondByFor` (bookings.repository: `readGarageCalendar` — pause, hours, closures in range, plain reads after the locks — then `garageRespondBy`). Null = no deadline: rows from before 0042 (never backfilled), unpaid bookings, a time the garage suggested (confirmed already). Every new path that writes a paid pending booking must set it
- **The switch**: `AUTO_CANCEL_UNANSWERED=on` (default off, so the team can tell garages first). While off the deadline is still computed, stored and shown (garage countdown, customer "by 10:42 am", admin, the digest) as guidance only: no 409, nothing cancelled. While on: the garage's **Accept and Suggest times** after `respond_by` are **409 `RESPONSE_TIME_PASSED`** (`assertCanStillAnswer` in `modules/garage-response/garage-response.rules.ts`), in the conditional writes too (`updateBookingStatus` guard `responseTimeLeftAt`; `insertProposal` `respondByAfter`). A booking the cron already cancelled for it is 409 whatever the switch says. Reject stays allowed (same refund)
- **The cron** (`POST /api/v1/ops/pending-digest`, after the suggestion sweep and before the refunds' retry, also in quiet hours — cancelling is not a message): `garageResponseService.sweep` takes paid (`payments.status = 'paid'`) pending bookings past `respond_by` with no open suggestion, oldest deadline first, `RESPONSE_SWEEP_LIMIT` 20 a run, and cancels each with `bookingsRepository.cancelNotAcceptedInTime`: one conditional write (still pending, paid, past the deadline, no open suggestion, car not collected) setting `cancelled_by = 'vendor'`, `response_missed_at`, reason `Not accepted in time`, then `closeWaitingOnBooking`. **An Accept racing it** is conditional on `pending` (and the deadline still ahead): exactly one wins, the loser reads 409/`BOOKING_STATE_CHANGED`. `cancelled_by = 'vendor'` is the representation on purpose: `lib/refunds.ts` owes the full payment, `autoRefundCause` is `garage_declined` (AUTO_REFUNDS sends it), Statistics and the pilot numbers count it with garage declines. `response_missed_at` (CHECK: only on a garage-side cancellation with a deadline) tells it apart: admin "Not accepted in time" (list, detail, Refunds reason `bookingRefundReason`), the garage's Cancelled card, the customer's page and Updates
- **An open "Suggest another time" is an answer**: no auto-cancel while one is open (its own expiry takes over). Withdrawing it (`bookingsRepository.withdrawProposal`, booking row then suggestion row) keeps the deadline or moves it to at least 15 minutes from now (`afterWithdraw`), never past the slot
- **Who sees what**: booking payloads (customer and garage, `toBookingResponse`) carry `responseDeadline { respondBy, enforced, windowMins } | null` and `notAcceptedInTime`. Garage portal (`components/response-countdown.tsx`, words in `packages/core/src/response-deadline.ts`): "Accept within 12 min", amber in the last 5; "Accept by 9:30 am" while further off than the window (clock waits for opening); past it with the switch on, "Not accepted in time — cancelled and refunded" and no buttons. Customer: "Waiting for <garage> to accept — by 10:42 am" (the cancellation promise only while enforced); after the auto-cancel "<Garage> didn't accept in time. Your full refund is on its way (5–7 working days)." and **Book another garage**: `GET /bookings/:id/other-garages` (`modules/garage-response`, the booking's customer only, else 404) — up to 3 live garages (`listPublicVendorPage`: same booking type and its reach rules, at least one of the booked services' categories, a package standing for its members' — `wantedCategories`, the garage itself excluded, nearest first, from the doorstep/pickup address or the garage's pin, 50 km for drop-in) built by `vendorCardsFor`, linked with `?mode=`. Updates: the cancellation row says "<Garage> didn't accept in time" with the refund. **No Home card**: nothing is left for the customer to do (must-act cards are things to answer or pay), so Updates only
- **Ops**: Telegram `not_accepted_in_time` per auto-cancel ("Not accepted in time: <garage>, booking #…, refund ₹X owed/started"); the 30-minute "waiting" nudge says "accept by …" / "time to accept ran out …"; the 07:00 roll-up adds yesterday's auto-cancels per garage (`missedYesterday`, and posts for that alone). Statistics → Breakdown → By garage shows "N not accepted in time" (`StatsGarageRow.notAcceptedInTime`)
- E2E fixtures for this feature use ids `id(2200)`–`id(2299)` and phones `90000022xx` only (`seedResponseDeadlineRows`, `VENDORS.response`, `VENDORS.responseOther`); `.env.e2e` has `AUTO_CANCEL_UNANSWERED=on`. Seeded bookings have no deadline, so the cron touches only that one

### Transaction tables

- `bookings` — central entity. `booking_type`: `doorstep` / `dropin` / `pickup` (0037; labels and per-type rules in `lib/booking-types.ts`, keyed exhaustively). `scheduled_at` is the start timestamp. Doorstep and pickup lat/lng/address snapshotted from user address
- `payments` — 1:1 with bookings. Cash bookings: `status: pending` → `status: collected` on job completion. `amount` is what came through Razorpay; `credit_amount` (0049) the part paid with Detlio credit, which goes back as credit (`credit_returned_at`), never through the refund rules (see Gift a wash)
- Refunds (0029) are recorded by ops after a refund done by hand in the Razorpay dashboard (`POST /admin/refunds`, Mark refunded), or sent through Razorpay from the app (0036, see Refunds through Razorpay). `payments`, `booking_intents` and `booking_charges` share five refund columns (`refunded_amount` is the running total of every refund so far; `refund_ref` (rfnd_… or null for UPI/bank, with `refund_note` saying how), `refunded_at`, `refunded_by` describe the latest); every refund is also a `refund_records` row (unique `refund_ref`, unique `(kind, target_id, refunded_before)`), written in the same transaction, and the write is conditional on the total the dialog saw (`expectedRefunded`). A full refund of a booking's payment moves it to `refunded`; a part refund leaves it `paid`. What is owed is decided only by `lib/refunds.ts`: a cancelled booking's paid payment (any canceller, garage no-show included) except a **customer no-show** and a booking the customer **moved** (a reschedule cancels the old row with its payment still `paid` — find it by `bookings.rescheduled_from_id`); a failed intent with a `payment_ref`; a paid bill on a cancelled booking (not a customer no-show; paid extra work on any booking that did not complete, a customer no-show included, 0041); a payment recorded on a cancelled (replaced/withdrawn/declined) bill. The refunds repository's SQL only narrows to candidates; keep it no narrower than the lib. Nothing that settles or fails a payment may write over `refunded` (see `settlePayment`, `markBookingPaid`)
- No-show money: a customer no-show keeps the payment, keeps the promo use spent (`DISCOUNT_HELD`/`DISCOUNT_REALIZED` and their pure twins in `discounts.predicates.ts`), and earns the garage its normal payout (`lib/earnings.ts`, labelled "Customer no-show" in earnings). A garage no-show is refunded in full and earns nothing
- `reviews` — unique on `booking_id`. Only allowed after `bookings.status = completed`
- `receipt_numbers` / `receipt_counters` (0030) — the customer receipt's number, `DTL/<FY>/<6-digit seq>` (`DTL/26-27/000123`, 16 chars; FY is 1 April–31 March in IST, `lib/receipts.ts`). **One per reschedule chain root** (`root_booking_id` = `originalBookingId ?? id`), issued once and **never reused or renumbered**, whatever later happens to the booking. **Gapless counter**: `allocateReceiptNumber` bumps the FY's `receipt_counters` row with `UPDATE … RETURNING` in the same transaction as the booking's own payment going through (`settlePayment`, `consumeIntent`, `markCashCollected`), so a rollback gives the number back — never a SEQUENCE. Not on a reschedule (the root has its number) or a final bill (printed on the booking's receipt). `GET /bookings/:id/receipt` issues a missing one as a safety net and logs a warning; if it can't, it answers 503 `RECEIPT_NUMBER_PENDING` and alerts ops. Any new path that marks a booking's payment paid/collected must call it. Because the bookings a number was issued on must stay, `DELETE /users/me` refuses an account that has one (409 `ACCOUNT_HAS_RECEIPTS`) rather than cascade into them
- `bookings.accepted_at` / `started_at` / `completed_at` — written by the same conditional update that moves the status (`updateBookingStatus`). Null on bookings from before 0028; never backfill a guessed time
- `job_photos` — a job's before/after photos (`stage`), the record either side points to in a dispute. Key always under `vendors/<vendorId>/job-photos/<bookingId>/` (the customer's own in its `customer/` folder, 0045). The garage's: before from `confirmed` until completion, after from `in_progress` until 1 hour after completion (no late fabrication), 6 per stage; nothing changes 7 days after completion (`lib/job-records.ts`). Customers see the garage's once the job is `in_progress`, and their own always. `uploaded_by_role` (`garage`/`customer`) and `angle` (0045); see Job photo standards
- `booking_charges` — money asked after checkout: `kind = 'final_bill'` of an inspection job, or `extra_work` (0041, see Suggested times and extra work). The final bill is the one of an inspection job (a booking with an `on_inspection` service), raised by the garage while `in_progress` or up to 3 days after completion. `amount_due = max(0, total_amount − paid_before)`; 0 is `not_needed` and nothing is refunded. `paid_before` is what the booking covers: its pre-discount `subtotal_amount` once its payment landed (`creditAtBooking`), never the discounted cash, so a promo code is not charged back and payout + balance equals the bill. Ops cancelling a booking withdraws its unpaid bill (`cancelBookingAsAdmin`); a payment that lands on a withdrawn, replaced or already-paid bill gets one refund note and one alert. At most one non-cancelled final bill per booking (partial unique index); an unpaid one is replaced by cancelling it, a paid one is locked. Settling is conditional on `status = 'due'` and the bill's own `gateway_order_id`, because the app's verify and the webhook both arrive (`lib/final-bill.ts`)

### Test data and the reset (0032)

- **Start pilot clean** (`modules/data-reset`, mounted at `/admin/data-reset`; rules in `lib/data-reset.ts`, runbook in `apps/server/docs/test-data-reset.md`) deletes test bookings with everything attached. Behind `ADMIN_DATA_RESET=on` (env, default off): while off every route is a 404 before auth runs and the admin nav hides it. Super-admin only. The owner runs it from admin after a backup; engineers and agents never run it, or any delete SQL, against production
- The unit is the **reschedule chain** (`coalesce(original_booking_id, id)`): in or out as a whole, never half. A chain goes with its items, payments, notes, job photos (rows, then R2 objects after commit, best effort), final bills, reschedules, promo uses, booking/bill `refund_records` and reviews, plus its consumed `booking_intents`; a cutoff run also takes checkouts with no booking opened before the cutoff, and their `refund_records` of kind `checkout` (no FK: deleted by hand). Garages, services, offers, notices, accounts and cars are never touched by the reset itself (deleting a garage forever from the Bin reuses its planner with the `garage` scope; see The garage Bin)
- **Real money is never deleted.** `gateway_mode` (`live` / `test` / `fake`, text + CHECK) on `payments`, `booking_intents` and `booking_charges` is written wherever an order is opened (`gatewayModeFor`, from the key id) and copied by `consumeIntent` and a reschedule. Never branch payment logic on it. Old rows (null) are classed by asking Razorpay in the dry run (`lookupRazorpayMode`, a time budget and a slice per call; answers are written back). Live, cash, unknown or unchecked money keeps the whole chain ("Real payment — kept"); a failed check is unknown, never deletable. - **Receipts: never renumbered.** Per financial year, a year whose receipts all belong to deleted chains, with no kept chain still owed one, **restarts** (its numbers, voids and counter go; the next is 000001). - The delete runs in one transaction: `SET LOCAL lock_timeout '5s'` / `statement_timeout '60s'`; checkout rows then booking rows FOR UPDATE in id order (batches of 500); the dry run and the delete read the whole scope (the planner applies the ticks, so the dry run, its CSV and the audit row list kept and unticked rows too) but only the ticked rows are locked; ticking more than a run's cap (300 chains, 1000 checkouts) is not refused, the planner takes the oldest and reports `overCap`; the plan recomputed from the locked rows and refused unless its `selectionHash` is the dry run's (409 `PREVIEW_STALE`) and the typed phrase matches (400 `CONFIRM_PHRASE_MISMATCH`); the audit row; receipts; deletes; then, last of all (lock order step 7), a restarting year's `receipt_counters` row FOR UPDATE, checked empty and deleted. ## Slot availability logic

Do NOT store slots in the DB. Generate them dynamically (`apps/server/src/lib/slots.ts`):

```ts
day        = dayStatus(paused?, holiday?, weekly hours)   // paused > holiday > weekly off day
day_slots  = starts from open_time every slot_interval_mins whose whole job
             (the sum of the services' durations) ends by close_time
noticed    = day_slots - starts sooner than the minimum notice (1h at garage, 3h doorstep and pickup)
busy       = bookings WHERE vendor_id = ? AND status IN (pending, confirmed, in_progress)
             AND payment is paid/collected, starting that IST day (or the day before)
             // each range = [scheduled_at, scheduled_at + bookings.duration_mins)
free_slots = noticed - starts where the peak number of busy jobs during the new
             job's range is already >= bays, or the day already has jobs_per_day jobs
```

- **Capacity**: `vendors.bays` is how many cars a garage works on at once (null or 0 = 1). `vendors.jobs_per_day` is an optional cap per IST day (null = no cap). Back-to-back jobs do not overlap; a booking holds capacity for its own `duration_mins` snapshot. Cancelled and completed bookings hold nothing.

The root's KEY SHARE is the lock the `receipt_numbers` foreign key check would otherwise take after the counter, so `allocateReceiptNumber` takes it first. Add any new lock to that list. Taken on their own, never alongside these: service media's, complaints', a customer's saved garages (`favourites:<userId>`), a garage's payouts (`payouts:<garage>`), and the refund lock (`refund:<payment>`, then only `auto-refunds:cap`, then the money row at the write; see Refunds through Razorpay).
- A paid pending booking carries its garage's deadline to answer, `respond_by` (0042, see Garage response deadline): written by every write that makes one: an hour before the slot at the latest, unless the 15-minute floor lifts it, and never past the slot.
- An unpaid booking holds nothing, so paying for one later is a booking write too: `POST /payments/orders` refuses a full/closed/paused garage up front, and `paymentsRepository.settlePayment` re-checks under the vendor-day lock when the money lands (a refusal cancels the booking and flags the payment for refund).
- A reschedule leaves the booking being moved out of the count, everywhere: the write, the pre-check, and the picker's list (`GET /vendors/:id/slots/reschedule/:bookingId`).
- Refusals: 409 `SLOT_FULL`, 400 `GARAGE_CLOSED_THAT_DAY`, 409 `GARAGE_PAUSED`. After payment they become refund-due intent failures (`slot_full`, `garage_closed`, `garage_paused`).

---

## Booking status flow

```
pending → confirmed → in_progress → completed
       → cancelled (from any state before completed)
```

---

## Payment status flow

```
Online:  pending → paid → refunded   (refunded only when a full refund is recorded or sent; a failed Razorpay refund puts it back to paid)
Cash:    pending → collected
Failed:  pending → failed
```



## Key constraints

- One review per booking — unique constraint on `reviews.booking_id`
- Doorstep bookings require `vendors.doorstep_enabled = true` and a matching `vendor_service_areas` row for the customer's location
- Drop-in bookings require `vendors.dropin_enabled = true`
- Vendor listings are only shown when `vendors.status = active` AND `vendors.is_verified = true` AND the garage is not paused and not in the Bin — `LISTED_TO_CUSTOMERS` / `isListedToCustomers` (`modules/vendors/vendors.predicates.ts`), the same rule as the admin list's Live. The garage page itself (`findPublicVendorById`, `vendorPageOpen`) skips the pause check so a paused garage's page still loads, but not the Bin check
- **A garage's contact details reach a customer only through a booking** (owner decision, 17 Oct 2026). `GET /vendors/:id` is an allow-list (`modules/vendors/vendors.public.ts` `toPublicVendor`): never phone, WhatsApp, email, street address, maps link, notes or other internal columns. The garage's phone, WhatsApp, address, pin and maps link are on the customer's own booking (`toBookingResponse`'s `vendor`, served only to the booking's customer or its garage) — the phone and WhatsApp only inside the contact window (see Contact windows). Detlio Certified is on it as one boolean, `certified` (0048). A new column on `vendors` stays off public payloads unless added to the allow-list on purpose; the same goes for any new public or customer-wide payload that names a garage
- A user can be both a customer and a vendor member — check `is_customer` independently of their mapping rows
- **The active `vendorId` is produced by `resolveTenant` and read from context. No handler, service or repository ever reads it from a request parameter** — that is what keeps `X-Vendor-Id` from turning every vendor endpoint into an IDOR candidate
- A mapping miss returns 404, never 403 — a 403 confirms the company exists and leaks the id space
- Every read of `user_member_mapping` must filter `status = 'active'`. Miss it in one place and a suspended member still has access
- The vendor-app login gate is "active seat **or** `is_vendor_owner`". The second clause is the onboarding window: `vendor_onboard` sets the flag when the OTP is verified, but the company — and so the mapping row — is not created until onboarding step 2. Member management keeps the flag in step with the seats, so this does not let a suspended member back in
- Vendor routes default deny: a new route under `/vendors/me` is `vendor_admin`-only until someone deliberately widens it with `requireVendorRole`
- The owner's mapping row cannot be removed, demoted **or suspended** by anyone, including the owner. That is what guarantees at least one active `vendor_admin` always exists. Ownership moves only by explicit transfer
- Vendor-facing booking payloads carry the customer's phone only inside the contact window (`user.phone` null outside it; see Contact windows), and no `vendorPayoutAmount`, `subtotalAmount`, `discountAmount` or `discountFundedBy` — money lives behind `GET /vendors/me/earnings` and `GET /vendors/me/earnings/statement`, both `vendor_admin`-only. Use `toVendorBookingResponse` for any new vendor endpoint. The final bill (`finalBill`, and `paidAtBooking`, what the booking covers toward it) is in the vendor payload on purpose: it is what the garage itself asked the customer for, not the payout split
- Job records are mounted under `/vendors/me/bookings/:id/{photos,final-bill}` and are deliberately widened to `vendor_operator` in their own route files — the people who do the work take the photos and write the bill. The customer pays a bill at `/bookings/:id/charges/:chargeId/{pay,verify}` and adds their own car photos at `/bookings/:id/photos` (0045); anyone but the booking's customer gets a 404
- A Razorpay order's notes name what it pays for: `intent_id`, `booking_id`, or `charge_id` (with its `booking_id`). The webhook checks `charge_id` first, then a bill by `gateway_order_id` (a payment can arrive without its order's notes)
