# Project: Detlio — agent instructions

## Stack

- **Framework**: Next.js (App Router)
- **Language**: TypeScript
- **Database**: PostgreSQL
- **ORM**: Drizzle ORM
- **Auth**: OTP (SMS) + Google OAuth, JWT access tokens + refresh tokens (HttpOnly cookies)
- **Payments**: Razorpay (online), cash on service
- **Storage**: Cloudflare R2 (S3 API, `lib/storage.ts`) for vendor, service and job photos; Cloudflare Stream (`lib/stream.ts`) for service videos. Photos go browser → R2 on a presigned URL, so the API never sees the bytes: every image upload re-encodes the file in the browser first (`stripImageMetadata`, `packages/core/src/image-upload.ts`) to drop EXIF/GPS. A new image upload path must do the same

## Rules

### Repository layout

This is a bun-workspaces monorepo driven by Turborepo. Four deployables:

```
apps/users      detlio.com          customer app
apps/vendors    vendor.detlio.com   vendor portal
apps/admin      admin.detlio.com    operations panel
apps/server     api.detlio.com      Hono API
packages/core   @repo/core          API client, types, stores, domain helpers
packages/ui     @repo/ui            shared components + globals.css
```

- Each frontend serves its routes at their real public paths. There is no
  middleware rewriting `/vendor/*` or `/admin/*` any more — a route's directory
  under `app/` is the URL it is served at. Do not reintroduce a path map.
- Surface-specific code lives in its app. `packages/*` is for code at least two
  apps use; `packages/core` must never import from `packages/ui`.
- The three frontends call `api.detlio.com` directly. Any new origin that needs
  to reach the API must be added to `corsOrigin` in `apps/server/src/lib/env.ts`.
- `apps/server/src/package.json` is a one-line ESM marker required by the Vercel
  build output. It is not a workspace — never add `apps/server/**` to the
  workspace globs, and do not delete or rename it.

### Database

- Do NOT run migrations when making schema changes
- Do NOT call `drizzle-kit push` or `drizzle-kit migrate`
- Only modify schema files — the developer runs migrations manually
- Production is migrated by `.github/workflows/release-api.yml` after E2E passes on `main`, before the API deploys. A new migration file must:
  - take the next number with no gap (`0026_…` after `0025_…`) and have a matching entry in `drizzle/meta/_journal.json`
  - run inside a single transaction — no `BEGIN`/`COMMIT`, `CONCURRENTLY` or `VACUUM`; a new enum value cannot be used in the same file that adds it
  - be additive relative to the code currently in production; drops and renames go in a later release, once nothing reads the old shape

Do not add another provider or call the SDK from anywhere else
- **The key lives only in the Vercel environment** (`OPENAI_API_KEY`), never in code or git (`.env.example` lists it empty). Unset means the feature is off: `GET /admin/ai/config` (one route for every AI helper) says `{ describe: false, pictures: false }` and the admin panel hides the buttons. The model is `AI_TEXT_MODEL` (default `gpt-5.5`), so it can change without a release
- **No personal data is ever sent**: no customer, owner or staff names, phones, addresses or booking details — only facts the garage page already shows (a service's name, category, pricing type, duration) and the garage's business name. Request schemas are `.strict()` so nothing else can ride along

- **The key lives only in the Vercel environment** (`OPENAI_API_KEY`), never in code or git (`.env.example` lists it empty). Request schemas are `.strict()` so nothing else can ride along. The one exception is the garage import below (owner decision, declared in the privacy policy's section 12): it sends the documents a garage gave us to join, never customers' data
- **AI text is a draft, never saved by the AI call**: `POST /admin/services/describe` only returns text for a form field, and every answer must pass `lib/copy-rules.ts` plus the description rules in `lib/service-description.ts` (1–2 plain sentences, at most 200 characters, no prices, no times unless given, no claims), with one retry; otherwise 422 `AI_NO_DESCRIPTION`. Any SDK error is 503 `AI_UNAVAILABLE`. Rate limited per admin per hour (`AI_DESCRIBE_RATE_LIMIT`, default 60)
- **Garage import** (`POST /admin/vendor-imports/extract`, `modules/vendor-imports`, rules in `lib/garage-import/`): photos and PDFs are read by `DocumentClient` (strict JSON-schema output, 50 s timeout, no retry — the API function's limit is 60 s in `vercel.json`); a Tally CSV is parsed by fixed rules with no AI (header → field table in `lib/garage-import/tally.ts`). The model only copies what is written; every decision is code: phones to 10 digits, "Call"/"on inspection" → On inspection with the fee missing, "from ₹X" → X to check, a missing duration is never guessed, the owner phone is always `check` (Create attaches the garage to whoever has that number — `POST /admin/vendor-imports/owner-account` says who). Drafts are held to the create endpoint's own zod schemas. **Files are never stored or logged** (memory for the one request; logs carry counts, sizes and timing only; every `responses.create` in `lib/ai.ts` sends `store: false`, or OpenAI keeps the response for 30 days), and **nothing is saved by the import**: the review screen creates the garage through the ordinary `POST /admin/vendors`, **always as Pending and not verified**. Errors: 503 `AI_UNAVAILABLE`, 422 `IMPORT_UNREADABLE`, 413 `IMPORT_TOO_LARGE`. Rate limited per admin per hour (`AI_IMPORT_RATE_LIMIT`, default 30)
- **Tests never call OpenAI**: unit tests pass a fake `TextClient` or `DocumentClient` (or, for the SDK client itself, a canned `fetch`); E2E runs with `AI_FAKE=1` (`.env.e2e`), which answers every request with `FAKE_AI_TEXT` and reads every photo or PDF as the same poster, `FAKE_GARAGE_READING` (`lib/garage-import/vision.ts`, asserted on by `specs/admin/garage-import.spec.ts`). The server refuses to boot with `AI_FAKE` set in production, like `E2E_FAKE_PAYMENTS`

### Module structure

Every feature module must follow this exact file structure:

```
module.route.ts        - route handlers
module.controller.ts   — request/response only, no business logic
module.service.ts      — business logic, orchestration
module.validation.ts   — zod schemas for request validation
module.repository.ts   — all DB queries via Drizzle ORM, no logic
```

- Controllers call services only
- Services call repositories only
- Repositories call the DB only — no business logic, no HTTP concerns
- Validation schemas live in `module.validation.ts` and are used in controllers before calling services

## Data model overview

### Auth tables

- `users` — single table for all user types. Flags: `is_customer`, `is_vendor_owner`. There is deliberately no `is_admin`: platform admin comes from a `super_admin` row in `user_member_mapping` or the env-credential break-glass login, never from a column or a JWT claim
- `user_member_mapping` — **the single role table for the whole product**: `(vendor_id, user_id, role, status)`. `role` is namespaced by scope — `user` / `super_admin` (both `vendor_id IS NULL`) and `vendor_admin` / `vendor_operator` (both `vendor_id NOT NULL`), enforced by a CHECK constraint. The absence of a row *is* the `user` role; baseline accounts are never materialized
- `otp_verifications` — stateless OTP log. `purpose`: `login` / `register` / `vendor_onboard`. `otp_code` holds a keyed hash of the code, never the code (`otpDigest` in `lib/otp.ts`: HMAC-SHA256 over purpose, phone and code, keyed from `JWT_SECRET`, cut to the column's 10 characters, compared with `otpMatches`). Each code sent deletes a batch of codes that expired over a day ago. Never log a code; the only print is `sendOtpSms`'s local-dev stand-in for the phone
- `refresh_tokens` — one row per session. Store SHA-256 hash of raw token, never plaintext

### Customer tables

- `user_addresses` — saved addresses with `lat/lng`. Doorstep location is snapshotted onto `bookings` at booking time
- `user_vehicles` — saved car profiles. `is_default` for auto-selection. `wash_interval_days` (0031) is the customer's wash reminder interval for Home's wash bar: 7/10/14/21/30 only (CHECK), null = the default, 14 days or 10 from 1 Oct to 31 Dec in IST (`lib/wash-status.ts`, Chennai-only and hard-coded). Set with `PATCH /users/me/vehicles/:id { washIntervalDays }`
- `users.updates_seen_at` (0031) — when the customer last opened Updates; anything after it is unread and lights Home's bell (null reads as `users.created_at`). `POST /users/me/updates/seen` only ever moves it forward, and never past the server's clock. 0031 set it to now for every existing account

### Vendor tables

- `vendors` — the company. `owner_id` names the one person who owns the business; `user_member_mapping` answers the separate question of who can use the portal and with what power. `is_verified` is flipped manually by admin. `slot_interval_mins` sets calendar granularity (30/45/60). `owner_id` cascades from `users`, so `DELETE /users/me` refuses an account that owns a garage (409 `VENDOR_OWNER_ACCOUNT`, `lib/account-deletion.ts`) rather than delete the garage and its bookings with it
- **Live** (customers can find the garage) is `status = 'active'` AND `is_verified` AND not paused (`bookings_paused_at IS NULL`) AND not in the Bin (`deleted_at IS NULL`, see The garage Bin). One definition: `LISTED_TO_CUSTOMERS` (SQL, alias `v`) and its twin `isListedToCustomers` in `modules/vendors/vendors.predicates.ts`, pinned together by its test. The customer lists and Home's Nearby run the SQL; the admin list's `live` flag is the twin. Change one, change both — never restate the conditions. **Active** is only the stage (approved by Detlio), and includes paused and unverified garages
- **Readiness** — the admin garage list's "what's missing" checklist, `lib/vendor-readiness.ts` (pure, unit-tested), returned per garage on `GET /admin/vendors` as `readiness` items `{ key, severity, label, detail?, short, tab }`, where `tab` is the edit page's `?tab=` that fixes it. **Blocking** (customers can't book it): no active plain services; neither drop-in nor doorstep on; no open day (no `vendor_working_hours` rows, or all closed). **Fix**: no pin, or pin not confirmed; services without a description (counted); `vehicle_types` empty or holding a retired label (compared case- and space-insensitively — seeds store `hatchback`/`suv`); bays null or 0. **Optional**: no logo; no photos; doorstep on with no radius and no drawn area (the 10 km default is used — owner decision). Only blocking and fix count as needing fixing. Not checked on purpose: distance from Chennai (garages in other towns are allowed), verification (that is the Verify button). Packages are left out of the services rules. `GET /admin/vendors` stays one full array (other screens' garage pickers read it); the panel's chips (`apps/admin/lib/vendor-list.ts`: All · Live · Active · Pending · Suspended · Archived · Bin, `?show=`, default Live) filter and count it on the client; a garage in the Bin is under Bin and in no other chip or count, and the Bookings garage filter leaves it out. Any admin write that changes what the list shows must invalidate `adminVendorKeys.lists()` (`useInvalidateAdminVendors`), since verify/archive/restore return the bare row without `live` or `readiness`
- `vendor_working_hours` — one row per day of week (0=Sun … 6=Sat). `is_closed` handles off days
- `vendor_service_areas` — pincodes/areas covered for doorstep jobs
- `vendor_photos` — ordered gallery. `sort_order` controls display sequence

### Catalog

- `services` — vendor-scoped. `category`: `car_wash` / `detailing` / `coating` / `scratch_removal` / `others` / `package`. `duration_mins` drives slot consumption
- `service_package_items` — composition of a package. A package is a `services` row with `category = 'package'` that bundles other services of the same vendor, so it books, prices and consumes slots exactly like a service and `bookings.service_id` stays a single FK. Its price and duration are vendor-set and independent of its members; the members exist to itemize contents and compute savings from their live prices
  - Listings that mean "plain services" MUST exclude `category = 'package'` (see `listServices`, and the admin repository — `listActiveServiceIds` especially, since the admin editor reconciles against it)
  - The booking path MUST NOT exclude packages — a package occupies a slot like any other service
  - Packages are created only via `/vendors/me/packages`; `POST /vendors/me/services` rejects `category: 'package'` because a package with no members is invalid
  - The admin editor's save sends the garage's full list and the server hides any live service missing from it, so the editor must never leave a typed-in row out: a row that is not ready blocks the save instead (`apps/admin/lib/service-rows.ts`). It sends `services` only when the Services tab has changes (`apps/admin/lib/garage-edit.ts` `dirtyTabs`). "How customers book" (`dropinEnabled` / `doorstepEnabled` / `doorstepRadiusKm`) is saved on tap by its own card above the tabs and is never part of Save changes, so the two can't overwrite each other. Ready-made services are `packages/core/src/service-templates.ts`; their descriptions pass the copy rules (tested on both sides). Admin hides and shows services one at a time with `PATCH /admin/vendors/:id/services/:serviceId/active` (plain services only; 409 `SERVICE_IN_PACKAGE` for one inside a package) and lists hidden ones at `GET /admin/vendors/:id/services/hidden`
- Category labels live in `apps/server/src/lib/categories.ts` and `packages/core/src/categories.ts`, both keyed exhaustively on the category union — add new categories there or the build fails

### Service photos and videos (0033)

- `service_images` holds a service's (or package's) photos **and** its video: `kind` `image`/`video`, `source` `upload`/`ai` (text + CHECK). At most `R2_MAX_IMAGES_PER_SERVICE` (3) photos and **one** video, checked in `serviceMediaService` (`modules/service-media`) by `insertMediaUnderLimit` under a per-service `pg_advisory_xact_lock('service-media:<id>')`, taken on its own and never alongside the booking-write locks (outside their order, like job photos'). Pure rules in `lib/service-media.ts`; garage photo routes stay `/vendors/me/services/:id/images…` (vendor_admin, `resolveTenant`) and admin's `/admin/services/:serviceId/images…`, both calling the shared service
- **The privacy tick**: every upload (photo or video, garage or admin) needs `consent: true` — "no number plates or faces can be read, or the owner agreed" — else 400 `MEDIA_CONSENT_REQUIRED`; `consent_confirmed_at` records it, `uploaded_by` names the admin or `'garage'`. A photo URL must sit in its own service's folder (`vendors/<vendorId>/services/<serviceId>/`)
- **Video** goes through Cloudflare Stream (`lib/stream.ts`, plain fetch, no SDK): a direct creator upload ≤ 200 MB or a tus upload above, `maxDurationSeconds` 60. The row is `video_status = 'processing'` until `POST /api/v1/webhooks/cloudflare-stream` (signed: `Webhook-Signature`, HMAC-SHA256 of `time.body`, 5 min tolerance) or the upload block's poll (`GET …/media/:mediaId`, which asks Stream) settles it to `ready` (`duration_secs`, `poster_url`) or `error` (`video_error`, plain words, never Stream's text); `settleVideo` only moves a processing row. **Replacing never loses the old video**: a ready video stays (customers keep seeing it) while its replacement uploads and processes, and is deleted only by `settleVideo` when the new one is ready, in the same transaction and lock (AI samples likewise go only then); if the new one fails or is removed, the old one stays. So a service may briefly hold a ready video plus one not-ready replacement, never more (`videoCountsOnStart`, `removedOnVideoStart`, `removedWhenVideoReady`). Off — slot hidden, routes 404 — unless all four `CLOUDFLARE_*` env vars are set. Removing or replacing deletes the Stream video (and a photo's R2 object) after the commit, best effort (`removeMediaFiles`)
- **AI sample pictures** (admin only, `OPENAI_API_KEY`, else `GET /admin/ai/config` → `pictures: false` and 404s; in the admin editor it is in each saved service's ⋯, "Photos and video"): two options from the official `openai` SDK (`AI_IMAGE_MODEL`), parked under `ai-temp/<serviceId>/` in R2 (a 1-day lifecycle rule clears leftovers), the chosen one copied into the service's folder as `source = 'ai'`. Only while the service has no real photo or video; a real photo, or a video once ready, removes the AI samples in the same transaction. The prompt is the admin's text cleaned of emails, phone numbers and plates, plus a fixed style — never personal data
- **Customers** get `toPublicMedia`: photos and *ready* videos only, `kind`/`url`/`posterUrl`/`durationSecs`/`source` — never `consent_confirmed_at`, `uploaded_by`, status or uid. Anything AI-made or drawn (the `packages/ui` sample art, chosen by `sampleArtFor`) is tagged "Sample"/"Sample image"; garage uploads "From <garage>". Videos play on tap only (`preload="none"`, hls.js loaded on the first Play)
- **Tests never call Cloudflare or OpenAI**: `STREAM_FAKE=1` (uploads land on `/api/v1/fake-stream`; `apps/e2e/support/stream.ts` fires the signed webhook) and `AI_FAKE=1` (a fixed PNG). Both are refused at boot in production, like `E2E_FAKE_PAYMENTS`. Setup for production: `apps/server/docs/service-media.md`

### The garage Bin (0034)

- **Archive and the Bin are different things** (owner decision, 16 Oct 2026). Archive (`status = 'archived'`) only hides a garage from customers; everything else carries on. The Bin is for garages being deleted: `vendors.deleted_at` set (with `deleted_by_name`, the typed name, and `deleted_reason`), stage, verification and pause left untouched so Restore brings back exactly what was there. Nothing in the Bin is deleted on its own
- **One rule, everywhere**: in the Bin is `deleted_at IS NOT NULL`, read only through `modules/vendors/vendors.predicates.ts` (`NOT_IN_BIN` for raw SQL over `vendors v`, `vendorNotInBin()` for Drizzle, `isInBin` for a row, `vendorPageOpen(id)` for the garage page's lookup). It is part of `LISTED_TO_CUSTOMERS` / `isListedToCustomers`, and every customer read that skips the list (garage page, services, packages, slots, hours, holidays, public reviews, checkout, `checkGarageCanTake`, `garageRefusalForBooking`, Book again, offers) must say it too. A new customer read of a garage that does not go through these is a bug
- **Its team is locked out**: every seat read in `members.repository` joins `vendors` and requires `vendorNotInBin()` beside the seat's own `status = 'active'` (two filters on two tables; neither stands in for the other). `resolveTenant`'s super_admin support path 404s a garage in the Bin, or one that does not exist, before it writes the access record. Seat rows are kept, so Restore gives access back as it was. Moving to the Bin, restoring and deleting forever re-sync every seat holder's `is_vendor_owner` in the same transaction (the vendor-app login is "active seat or the flag"), so someone who also has a live garage keeps their login and someone who does not loses it
- **Admin**: `modules/vendor-bin` (super-admin; `GET /admin/vendors/:id/bin-preview`, `POST …/bin { actorName, reason? }`, `POST …/restore { actorName }`, `GET …/delete-preview`, `DELETE /admin/vendors/:id { actorName, confirmName, selectionHash }`). Every action writes `admin_audit_log` (`garage_binned`, `garage_restored`, `garage_deleted`) with the typed name, and locks the garage row FOR UPDATE first. Any other admin write on a garage in the Bin is 409 `VENDOR_IN_BIN` (`assertWritableVendor` in admin.service, `resolveService` for admin media); reads still work, and the edit page opens read-only. Admin pickers (discounts, notices, the Bookings filter, demand/supply) leave the Bin out
- **Moving to the Bin with bookings to come is allowed**: each pending, confirmed or in-progress booking is cancelled after the commit through the admin cancel (`adminService.cancelBooking`, Detlio's own decision, reason "Garage removed"), so a paid one is a refund owed by `lib/refunds.ts` like any Detlio cancellation: refunded from the Refunds page, or by the automatic mode when `AUTO_REFUNDS` is on (the Bin itself never calls Razorpay). One that can't be cancelled (changed meanwhile) is listed in the answer
- **Delete forever** is only for a garage in the Bin (409 `VENDOR_NOT_IN_BIN`), with its name typed (400 `CONFIRM_NAME_MISMATCH`) and the preview's `selectionHash` (409 `PREVIEW_STALE`). It is the test-data reset's planner and deletes with the `garage` scope (every chain and every checkout of the garage, whenever made; `deletePlannedRows`, `finishRestarts`), so money classes, the receipt plan and the lock order are the reset's. Razorpay is never asked from here: null-mode money counts as unconfirmed and is kept (the reset's dry run records modes first). Then `lib/vendor-bin.ts` `purgeOutcome`: nothing kept → the garage row is deleted, in this order because of the RESTRICT diamond (package items, the plan's checkouts and bookings, services nothing points at, then the garage, whose cascade takes notices, garage-only offers and support-access rows; their counts go in the audit row); something kept → a tombstone (`purged_at`; business name, address, city, pincode and owner kept for receipts; phone, email, WhatsApp, maps link, logo and notes cleared; gallery, service media, package items, hours, closures, areas and seats deleted; services a kept booking names stay, off sale; garage-only offers switched off); over the reset's per-run cap → `partial`, the oldest deleted and the garage left in the Bin. A tombstone is in no admin list and its detail is a 404. R2 files (logo, gallery, service photos and AI pictures, job photos of deleted bookings) and Stream videos go after the commit, best effort; Telegram gets "Garage deleted by <name>: <garage>, N bookings"
- `countOwnedVendors` (the cap on companies) counts a garage in the Bin but not a tombstone

### Complaints (0035)

- `complaints` — a customer's complaint with its number and clock (owner decision, 17 Oct 2026). Raised by a signed-in customer from a booking's Help sheet (booking and garage attached; the booking must be their own, anyone else's is a 404) or from the Contact page (neither): `POST`/`GET /users/me/complaints`, `modules/complaints`. The user id is always the session's; the schema is `.strict()`
- **The number** is `C-` and six digits (`formatComplaintNumber`), from `complaint_number_seq`: a SEQUENCE on purpose, so customers never wait on each other; a rolled-back insert leaves a gap. Not like receipt numbers, which must be gapless
- **The clock**: acknowledge within 24 hours, resolve within 7 days of `created_at`. The numbers live in `packages/core/src/complaints.ts`, which the legal pages (`GRIEVANCE_TIMELINES`), the customer app and admin read; `apps/server/src/lib/complaints.ts` is its twin (parity test). Overdue = open past acknowledge-by, or open/acknowledged past resolve-by (`complaintOverdue`); the admin list's SQL uses `overdueCutoffs`, never restated hours
- Status `open → acknowledged → resolved`, or `closed` (from any but closed; nothing reopens). Resolve needs `resolution_note`, which the customer reads; resolving or closing an open one stamps `acknowledged_at` then. `admin_note` never leaves admin. Moves are conditional updates (`COMPLAINT_ACTION_FROM`); a stale press is 409 `COMPLAINT_STATUS_CHANGED`. CHECKs in 0035 tie each status to its timestamps
- Every FK (`user_id`, `booking_id`, `vendor_id`) is `ON DELETE SET NULL`, and name, phone, booking reference and garage name are snapshotted, so `DELETE /users/me`, the reset and Delete forever keep the complaint
- Limits per customer (`complaintSubmitRefusal`): 5 open or acknowledged (409 `COMPLAINT_LIMIT_OPEN`), 3 an hour (429 `COMPLAINT_RATE_LIMIT`), counted under a per-customer advisory lock (`complaints:<userId>`) taken on its own, never alongside the booking-write locks
- A new complaint alerts ops on Telegram (`complaint_received`, Production only, the customer's words through `quoted()`). Start pilot clean takes a cutoff run's complaints as one row with one tick (`only.complaints`)

### Refunds through Razorpay (0036)

- **Refund now** (`POST /admin/refunds/send { kind, id, amount?, expectedRefunded?, note? }`, super-admin, `.strict()`) sends a refund through Razorpay (`lib/razorpay.ts` `createRazorpayRefund`: `POST /v1/payments/:id/refund`, speed `normal` only — instant costs extra — amount in paise, notes `detlio_kind`/`detlio_id`/`detlio_source` plus `booking_id`/`intent_id`/`charge_id`, `X-Refund-Idempotency` from `refundIdempotencyKey`) and records it exactly like Mark refunded (`refund_ref`, `refunded_by` the admin, `refund_note` "Sent through Razorpay from the app by …"). Amount defaults to everything owed, may be lower, never higher. Mark refunded stays for refunds done in the dashboard
- **Never twice, never more than paid.** Every send, under the payment's lock, first reads `GET /v1/payments/:id/refunds` and records any refund we have no record of (`source = 'razorpay'`, or ours by its notes when an answer was lost) and settles our pending ones Razorpay has finished; a found refund that doesn't fit what is owed stops it (409 `REFUND_RAZORPAY_MISMATCH`, alert). Only then is what is still owed (`lib/refunds.ts`) sent. If Razorpay can't be read, nothing is sent (503). A sheet whose figures moved sends nothing (409 `REFUND_STATE_CHANGED`)
- **The refund lock**: `pg_advisory_xact_lock('refund:<Razorpay payment id>')` (or `refund:<kind>:<id>` without one), `refundsRepository.withRefundLock`, held across the Razorpay calls, by Refund now, Mark refunded, the automatic mode and the refund webhooks. Taken on its own, never alongside the booking-write locks; the automatic mode then takes `auto-refunds:cap`; the money row's own lock comes last at the write. The button and the automatic mode try-lock (409 `REFUND_BUSY` / skip); the webhook waits. With one DB connection, everything inside goes through the `tx` (`Conn`); a query on `db` there would deadlock
- **`refund_records` (0036)**: `source` (`recorded` / `razorpay` / `admin` / `auto`), `gateway_status` (`pending` / `processed` / `failed`, null = never asked), `settled_at`, `failure_reason`. A refund Razorpay refused outright is a `failed` row with no refund id. `refund.failed` (or a check finding it failed) marks the row failed, takes it off the money row's total (a full refund's payment goes back to `paid`, the row describes the latest standing refund again), notes the booking and alerts: the money is owed again. The one-per-starting-total index leaves failed rows out. **Every reader of the history excludes failed rows** (`STANDING_REFUND`; the receipt, Home/Updates). `refund.processed` marks it processed. The webhook only touches refunds recorded here; it routes `refund.*` before any payment handling
- **Automatic mode** (`AUTO_REFUNDS=on`, default off; while off nothing runs and nothing is read). `refundsService.queueAutoRefund` after the cancel commits (customer cancel, garage decline, admin cancel incl. the Bin, garage no-show, `settlePayment`'s refusal, `failIntent`), via `runInBackground`; plus `sweepAutoRefunds` in the pending-digest cron (20 a run, 15 s budget, stops at the cap or when Razorpay is down). Rules in `lib/refund-sending.ts` `autoRefundHold`: never `bill`, never when anything was already refunded (no part amounts), never with an open/acknowledged complaint, only clear-cut causes (`autoRefundCause`), owed within the last 3 days, at most 3 failed tries. Daily cap `AUTO_REFUND_DAILY_CAP_INR` (default 20000, IST day, counted from `source = 'auto'` standing rows): the first refund that would pass it writes `auto_refund_cap_days` and alerts once; no more automatic refunds that day
- `E2E_FAKE_PAYMENTS` mints `rfnd_e2e_…` refunds in memory (same key, same refund; listable per payment), status `pending`
- Telegram: `refund_sent` (one per refund, auto/admin), `refund_failed` (one per failure), `auto_refund_cap_reached`. Customer: while an app-sent refund is pending, `refund.started` makes the booking page say "Refund of ₹X started on <date>. It reaches your account in 5–7 working days." (`customerRefundLine`)

### Pickup & drop (0037)

- The garage collects the car from the customer's address, works on it at the garage and brings it back (owner decisions, 17 Oct 2026). Rules in `lib/pickup.ts` (pure, unit-tested), words and numbers twinned in `packages/core/src/pickup.ts` (`pickup.parity.test.ts`, which also pins the booking type labels and notice)
- **On** = `vendors.pickup` `'yes'` (legacy `'nearby'` counts) **and** `pickup_terms_accepted_at` set: `isPickupOffered`, SQL twin `PICKUP_OFFERED` in `vendors.predicates.ts`. Never test `pickup = 'yes'` alone: onboarding answers from before 0037 have no terms and are not on. Turning it on always needs the responsibility tick ("We are responsible for the customer's car from pickup until it is returned"; admin: "The garage has agreed to this (signed agreement)"), recorded afresh with who and when (`planPickupChange`); off never does. Only `PATCH /vendors/me/job-types` (owner/admin seat, not a support session) and the admin vendor create/update write it; it is not a `PATCH /vendors/me` profile field
- Reach: the garage's `pickup_radius_km` from its pin, empty = `DEFAULT_PICKUP_RADIUS_KM` (10). Listing (`bookingType=pickup`) and the booking write both use it; no drawn area, no customer radius. A pickup booking needs a pinned saved address inside it. Services are the garage's normal (at-garage) services. Price is the services; `bookingTypeFee` is the one place a fee goes (0 until the owner decides)
- Steps: Accept → Picked up (customer's pickup code) → At garage → Mark in progress → Out for delivery → Delivered (delivery code), which completes it. `nextPickupStep` / `pickupStepRefusal` decide; each write is conditional on that state (bookings.repository `markPickedUp` …). `/complete` is refused for pickup. Once picked up, the customer cannot cancel or reschedule (also in the conditional writes)
- Codes: two different 4-digit codes from `crypto.randomInt`, written with the booking (every insert path, carried by a reschedule), stored plain because the customer's app shows them. **Only the customer's own booking payload carries them** (`customerPickupView`); `toVendorBookingResponse` replaces it with `vendorPickupView` (steps, `nextStep`, tries left), admin gets tries left and overrides. Never add them to another payload, alert or log. 5 wrong tries lock a code; Detlio then confirms the step from admin (`POST /admin/bookings/:id/pickup-step`, name stored on the booking, reason in the notes)
- Ops: the pending digest lists accepted, paid pickup jobs 30 minutes past their slot with no Picked up
- Customer app: `?mode=pickup` is a choice like the other two (`parseBookingType`); the switches list `offeredBookingTypes(vendor)` and show only with two or more, and `resolveBookingType` falls back when a garage stops collecting. Checkout's early "outside this garage's pickup area" is `insidePickupReach` (straight-line km from the garage page's `pickupRadiusKm`, a hair of slack); the server's OUTSIDE_PICKUP_RADIUS is the one that counts. The responsibility line before Pay is `PICKUP_RESPONSIBILITY_LINE`; the summary's fee line is `pickupFeeLabel` ("Free" while `bookingTypeFee` is 0). The booking page's timeline, code card and change lock are `pickupTimeline`, `pickupCodeCard`, `carWithGarage` (packages/core/src/pickup.ts). Home's tile carries `pickupStage` (`customerPickupStage`, twin `pickupStageOf`); Updates reads the step times, never the codes. The pickup listing leaves out garages with no pin

### Transaction tables

- `bookings` — central entity. `booking_type`: `doorstep` / `dropin` / `pickup` (0037; labels and per-type rules in `lib/booking-types.ts`, keyed exhaustively). `scheduled_at` is the start timestamp. Doorstep and pickup lat/lng/address snapshotted from user address
- `payments` — 1:1 with bookings. Cash bookings: `status: pending` → `status: collected` on job completion
- Refunds (0029) are recorded by ops after a refund done by hand in the Razorpay dashboard (`POST /admin/refunds`, Mark refunded), or sent through Razorpay from the app (0036, see Refunds through Razorpay). `payments`, `booking_intents` and `booking_charges` share five refund columns (`refunded_amount` is the running total of every refund so far; `refund_ref` (rfnd_… or null for UPI/bank, with `refund_note` saying how), `refunded_at`, `refunded_by` describe the latest); every refund is also a `refund_records` row (unique `refund_ref`, unique `(kind, target_id, refunded_before)`), written in the same transaction, and the write is conditional on the total the dialog saw (`expectedRefunded`). A full refund of a booking's payment moves it to `refunded`; a part refund leaves it `paid`. What is owed is decided only by `lib/refunds.ts`: a cancelled booking's paid payment (any canceller, garage no-show included) except a **customer no-show** and a booking the customer **moved** (a reschedule cancels the old row with its payment still `paid` — find it by `bookings.rescheduled_from_id`); a failed intent with a `payment_ref`; a paid bill on a cancelled booking (not a customer no-show); a payment recorded on a cancelled (replaced/withdrawn) bill. The refunds repository's SQL only narrows to candidates; keep it no narrower than the lib. Nothing that settles or fails a payment may write over `refunded` (see `settlePayment`, `markBookingPaid`)
- No-show money: a customer no-show keeps the payment, keeps the promo use spent (`DISCOUNT_HELD`/`DISCOUNT_REALIZED` and their pure twins in `discounts.predicates.ts`), and earns the garage its normal payout (`lib/earnings.ts`, labelled "Customer no-show" in earnings). A garage no-show is refunded in full and earns nothing
- `reviews` — unique on `booking_id`. Only allowed after `bookings.status = completed`
- `receipt_numbers` / `receipt_counters` (0030) — the customer receipt's number, `DTL/<FY>/<6-digit seq>` (`DTL/26-27/000123`, 16 chars; FY is 1 April–31 March in IST, `lib/receipts.ts`). **One per reschedule chain root** (`root_booking_id` = `originalBookingId ?? id`), issued once and **never reused or renumbered**, whatever later happens to the booking. **Gapless counter**: `allocateReceiptNumber` bumps the FY's `receipt_counters` row with `UPDATE … RETURNING` in the same transaction as the booking's own payment going through (`settlePayment`, `consumeIntent`, `markCashCollected`), so a rollback gives the number back — never a SEQUENCE. Not on a reschedule (the root has its number) or a final bill (printed on the booking's receipt). `GET /bookings/:id/receipt` issues a missing one as a safety net and logs a warning; if it can't, it answers 503 `RECEIPT_NUMBER_PENDING` and alerts ops. Any new path that marks a booking's payment paid/collected must call it. Because the bookings a number was issued on must stay, `DELETE /users/me` refuses an account that has one (409 `ACCOUNT_HAS_RECEIPTS`) rather than cascade into them
- `bookings.accepted_at` / `started_at` / `completed_at` — written by the same conditional update that moves the status (`updateBookingStatus`). Null on bookings from before 0028; never backfill a guessed time
- `job_photos` — a job's before/after photos (`stage`), the garage's evidence in a dispute. Key always under `vendors/<vendorId>/job-photos/<bookingId>/`; before from `confirmed`, after from `in_progress`, 6 per stage, frozen 7 days after completion (`lib/job-records.ts`). Customers see them once the job is `in_progress`
- `booking_charges` — money asked after checkout; today only `kind = 'final_bill'` of an inspection job (a booking with an `on_inspection` service), raised by the garage while `in_progress` or up to 3 days after completion. `amount_due = max(0, total_amount − paid_before)`; 0 is `not_needed` and nothing is refunded. `paid_before` is what the booking covers: its pre-discount `subtotal_amount` once its payment landed (`creditAtBooking`), never the discounted cash, so a promo code is not charged back and payout + balance equals the bill. Ops cancelling a booking withdraws its unpaid bill (`cancelBookingAsAdmin`); a payment that lands on a withdrawn, replaced or already-paid bill gets one refund note and one alert. At most one non-cancelled bill per booking (partial unique index); an unpaid one is replaced by cancelling it, a paid one is locked. Settling is conditional on `status = 'due'` and the bill's own `gateway_order_id`, because the app's verify and the webhook both arrive (`lib/final-bill.ts`)

### Test data and the reset (0032)

- **Start pilot clean** (`modules/data-reset`, mounted at `/admin/data-reset`; rules in `lib/data-reset.ts`, runbook in `apps/server/docs/test-data-reset.md`) deletes test bookings with everything attached. Behind `ADMIN_DATA_RESET=on` (env, default off): while off every route is a 404 before auth runs and the admin nav hides it. Super-admin only. The owner runs it from admin after a backup; engineers and agents never run it, or any delete SQL, against production
- The unit is the **reschedule chain** (`coalesce(original_booking_id, id)`): in or out as a whole, never half. A chain goes with its items, payments, notes, job photos (rows, then R2 objects after commit, best effort), final bills, reschedules, promo uses, booking/bill `refund_records` and reviews, plus its consumed `booking_intents`; a cutoff run also takes checkouts with no booking opened before the cutoff, and their `refund_records` of kind `checkout` (no FK: deleted by hand). Garages, services, offers, notices, accounts and cars are never touched by the reset itself (deleting a garage forever from the Bin reuses its planner with the `garage` scope; see The garage Bin)
- **Real money is never deleted.** `gateway_mode` (`live` / `test` / `fake`, text + CHECK) on `payments`, `booking_intents` and `booking_charges` is written wherever an order is opened (`gatewayModeFor`, from the key id) and copied by `consumeIntent` and a reschedule. Never branch payment logic on it. Old rows (null) are classed by asking Razorpay in the dry run (`lookupRazorpayMode`, a time budget and a slice per call; answers are written back). Live, cash, unknown or unchecked money keeps the whole chain ("Real payment — kept"); a failed check is unknown, never deletable. So does an unpaid order that may be live (mode `live`, or null and not answered `test`) while it could still be captured: a booking not cancelled, a bill still `due`, or within 24 h of the cancel, the bill's withdrawal or the checkout's expiry (`open_order`, "Payment may still arrive — kept"); a webhook for a deleted booking only logs. What a lookup answer means is `classifyModeLookup` in `lib/gateway-mode.ts` (pure, unit-tested); `lib/razorpay.ts` only fetches. Tests never reach Razorpay (`E2E_FAKE_PAYMENTS`)
- **Receipts: never renumbered.** Per financial year, a year whose receipts all belong to deleted chains, with no kept chain still owed one, **restarts** (its numbers, voids and counter go; the next is 000001). Any other year **voids**: the numbers move to `receipt_number_voids` (no FK to bookings; `audit_id` → `admin_audit_log`) and the counter is left alone. A voided number counts as issued for the gapless check. There is no renumber mode
- The delete runs in one transaction: `SET LOCAL lock_timeout '5s'` / `statement_timeout '60s'`; checkout rows then booking rows FOR UPDATE in id order (batches of 500); the dry run and the delete read the whole scope (the planner applies the ticks, so the dry run, its CSV and the audit row list kept and unticked rows too) but only the ticked rows are locked; ticking more than a run's cap (300 chains, 1000 checkouts) is not refused, the planner takes the oldest and reports `overCap`; the plan recomputed from the locked rows and refused unless its `selectionHash` is the dry run's (409 `PREVIEW_STALE`) and the typed phrase matches (400 `CONFIRM_PHRASE_MISMATCH`); the audit row; receipts; deletes; then, last of all (lock order step 7), a restarting year's `receipt_counters` row FOR UPDATE, checked empty and deleted. A busy row rolls the whole run back (503 `RESET_BUSY`)
- `admin_audit_log` — append-only (a trigger refuses UPDATE and DELETE), no FKs. `actor_sub` is the session, `actor_name` the name typed (the shared admin login is always 'admin'). The snapshot stores ids, references, amounts, Razorpay ids and receipt numbers, never phone numbers
- `bookings.marked_test_at` / `marked_test_by` — ops' "Test" mark (`POST`/`DELETE /admin/bookings/:id/mark-test`), set on the whole chain and copied by a reschedule. Display and pilot numbers only (`listBookingsCreatedSince`, `listAcceptsSince`, `listIntentsCreatedSince` leave marked bookings out); slots, refunds and receipts never read it. One marked chain can be deleted on its own (scope `chains`, which refuses an unmarked chain)

### Home hub (0031)

- `GET /users/me/home` and `GET /users/me/updates` are mounted inside the users routes (`modules/home`, no second auth). Both are derived on every read; there is no event table. Updates covers the last 30 days, capped at 100 rows (`lib/home-updates.ts`); a step with no recorded time is skipped, never guessed. Order on Home (owner decision): one must-act card (bill due, then garage shut on a booking's day; `lib/home-cards.ts`) above the offers, "Rate your wash" below them only when there is no must-act card — at most two cards above the car. A notice about the customer's own booking is never a card: it rides on the Next booking tile and leads Updates
- The Home read is about a dozen sequential queries. Production keeps one connection (`db/index.ts`, `PG_POOL_MAX` unset); `Promise.all` would not parallelise them there. The e2e suite sets `PG_POOL_MAX` so its workers are not queued on that one connection. Keep the count low and every booking read bounded by the 30-day window. Each optional part (offers, notices, closures, last wash, Book again, nearby) is isolated: a failure returns that part as null and is reported, and Home still renders
- Money in a Drizzle relational read's nested rows (`with: { payment, charges, … }`) comes back through JSON, so `numeric(10,2)` 800.00 arrives as `"800"`. `modules/home/home.mappers.ts` puts the two decimals back; do the same in any new nested read that returns money. Book again judges its garage like the garage page does (active, verified, not paused, still offering that booking type) and needs a map pin only for doorstep (`garageTakesJobAgain`); offers and Nearby keep the pin rule
- `discounts` Home fields: `show_on_home`, `home_title` (3–40 chars so it fits the coupon card's two lines, required with `ends_at` while shown — CHECK, and checked on the merged row in `discountsService`), `home_priority` 0 Normal / 1 High / 2 Top, `home_audience` (text + CHECK: `everyone` / `new_customers` / `booked_this_garage` / `near_this_garage` / `wash_due` / `car_type`), `home_audience_radius_km` (near only, default 10), `home_audience_vehicle_types` (car_type only). The card's small print is generated from the code's columns (`lib/offers.ts`), never typed. At most 3 offers: priority, then (targeting on) the customer's tie to the garage, then ends soonest, then newest. Limits are counted with `DISCOUNT_HELD` (`countHeldMany`), like `resolveDiscount`
- **The audience is display targeting only.** It decides who sees the card on Home; it never changes who may type the code at checkout — `resolveDiscount` must not read it. Every audience but `everyone` uses booking history, location or the customer's cars, so all of them are gated by `HOME_OFFER_TARGETING` (env, default off): while off, only `everyone` offers are shown, none of that data is read for offers, and the admin API refuses to set any other audience (409 `TARGETING_DISABLED`). Turn it on only in the release that updates the privacy policy. `GET /admin/discounts/home-config` tells the admin form; `GET /admin/discounts/home-reach` gives its "Estimated reach" by asking Home's own `offerSkipReason` of every customer (`lib/offer-reach.ts`), reading only the facts the chosen audience needs ("near" is measured from saved addresses there, since Home's live location is never stored). The admin preview's small print is a twin of `offerMetaLine` in `packages/core/src/offer-preview.ts`, and the notice link rule of `isAllowedNoticeLink` in `packages/core/src/notice-link.ts`, each with a parity test in `apps/server/src/lib`
- `notices` — team messages for Home and Updates: to everyone (`all`) or to customers with an upcoming booking in a window, optionally at one garage (`with_booking_between`). Never deleted: "End now" ends a live one at now and switches a scheduled one off (`lib/notices.ts`; an end before the start breaks the window CHECK). Links are `https://…` or an app path, never `//host`, and never contain a backslash or whitespace (browsers read `/\evil.com` as `//evil.com`); the CHECK and `isAllowedNoticeLink` hold the same rule. Titles, bodies and link labels, like offer titles, pass `lib/copy-rules.ts` (twinned in `packages/core/src/copy-rules.ts`, with a parity test). Not the legal change-notice channel (Terms §19, Privacy §13 promise WhatsApp or a call)
- `notice_dismissals`, `offer_dismissals` — a customer's × on a notice or an offer, kept on the server so it holds on every device; both cascade with the user. `bookings.review_prompt_dismissed_at` is the × on "Rate your wash" (`POST /bookings/:id/review-prompt/dismiss`, owner only, 404 otherwise)

## Slot availability logic

Do NOT store slots in the DB. Generate them dynamically (`apps/server/src/lib/slots.ts`):

```ts
day        = dayStatus(paused?, holiday?, weekly hours)   // paused > holiday > weekly off day
day_slots  = starts from open_time every slot_interval_mins whose whole job
             (the sum of the services' durations) ends by close_time
noticed    = day_slots - starts sooner than the minimum notice (1h at garage, 3h doorstep and pickup)
busy       = bookings WHERE vendor_id = ? AND status IN (pending, confirmed, in_progress)
             AND payment is paid/collected, starting that IST day (or the day before)
             // each range = [scheduled_at, scheduled_at + bookings.duration_mins)
free_slots = noticed - starts where the peak number of busy jobs during the new
             job's range is already >= bays, or the day already has jobs_per_day jobs
```

- **Capacity**: `vendors.bays` is how many cars a garage works on at once (null or 0 = 1). `vendors.jobs_per_day` is an optional cap per IST day (null = no cap). Back-to-back jobs do not overlap; a booking holds capacity for its own `duration_mins` snapshot. Cancelled and completed bookings hold nothing.
- **Holidays**: a `vendor_closures` row for the IST date makes it a closed day (`isClosed: true, closedReason: 'holiday'`). **Paused**: `vendors.bookings_paused_at` set means no slots on any day (`paused: true`), no checkout, and absent from every public list/search/map — but the garage page still loads. Neither touches existing bookings.
- The same rules run twice: in the slot list / pre-payment checks, and again inside the transaction that writes the booking (`checkGarageCanTake` in bookings.repository.ts) under a per-garage-per-IST-day advisory lock. Keep the two in step — both read the pure functions in `lib/slots.ts`.
- Advisory locks are always taken in one order: vehicle → reschedule chain → the booking's own row (FOR UPDATE when moving it, FOR NO KEY UPDATE in `settlePayment`) → vendor-day → discount → the chain root's row FOR KEY SHARE → the receipt counter's row lock, last of all; nothing is locked after it (see the comment above `lockVehicle`). The root's KEY SHARE is the lock the `receipt_numbers` foreign key check would otherwise take after the counter, so `allocateReceiptNumber` takes it first. Add any new lock to that list. Taken on their own, never alongside these: service media's, complaints', and the refund lock (`refund:<payment>`, then only `auto-refunds:cap`, then the money row at the write; see Refunds through Razorpay).
- An unpaid booking holds nothing, so paying for one later is a booking write too: `POST /payments/orders` refuses a full/closed/paused garage up front, and `paymentsRepository.settlePayment` re-checks under the vendor-day lock when the money lands (a refusal cancels the booking and flags the payment for refund).
- A reschedule leaves the booking being moved out of the count, everywhere: the write, the pre-check, and the picker's list (`GET /vendors/:id/slots/reschedule/:bookingId`).
- Refusals: 409 `SLOT_FULL`, 400 `GARAGE_CLOSED_THAT_DAY`, 409 `GARAGE_PAUSED`. After payment they become refund-due intent failures (`slot_full`, `garage_closed`, `garage_paused`).

## Key constraints

- One review per booking — unique constraint on `reviews.booking_id`
- Doorstep bookings require `vendors.doorstep_enabled = true` and a matching `vendor_service_areas` row for the customer's location
- Drop-in bookings require `vendors.dropin_enabled = true`
- Vendor listings are only shown when `vendors.status = active` AND `vendors.is_verified = true` AND the garage is not paused and not in the Bin — `LISTED_TO_CUSTOMERS` / `isListedToCustomers` (`modules/vendors/vendors.predicates.ts`), the same rule as the admin list's Live. The garage page itself (`findPublicVendorById`, `vendorPageOpen`) skips the pause check so a paused garage's page still loads, but not the Bin check
- A user can be both a customer and a vendor member — check `is_customer` independently of their mapping rows
- **The active `vendorId` is produced by `resolveTenant` and read from context. No handler, service or repository ever reads it from a request parameter** — that is what keeps `X-Vendor-Id` from turning every vendor endpoint into an IDOR candidate
- A mapping miss returns 404, never 403 — a 403 confirms the company exists and leaks the id space
- Every read of `user_member_mapping` must filter `status = 'active'`. Miss it in one place and a suspended member still has access
- The vendor-app login gate is "active seat **or** `is_vendor_owner`". The second clause is the onboarding window: `vendor_onboard` sets the flag when the OTP is verified, but the company — and so the mapping row — is not created until onboarding step 2. Member management keeps the flag in step with the seats, so this does not let a suspended member back in
- Vendor routes default deny: a new route under `/vendors/me` is `vendor_admin`-only until someone deliberately widens it with `requireVendorRole`
- The owner's mapping row cannot be removed, demoted **or suspended** by anyone, including the owner. That is what guarantees at least one active `vendor_admin` always exists. Ownership moves only by explicit transfer
- Vendor-facing booking payloads carry no `vendorPayoutAmount`, `subtotalAmount`, `discountAmount` or `discountFundedBy` — money lives behind `GET /vendors/me/earnings`, which is `vendor_admin`-only. Use `toVendorBookingResponse` for any new vendor endpoint. The final bill (`finalBill`, and `paidAtBooking`, what the booking covers toward it) is in the vendor payload on purpose: it is what the garage itself asked the customer for, not the payout split
- Job records are mounted under `/vendors/me/bookings/:id/{photos,final-bill}` and are deliberately widened to `vendor_operator` in their own route files — the people who do the work take the photos and write the bill. The customer pays a bill at `/bookings/:id/charges/:chargeId/{pay,verify}`; anyone but the booking's customer gets a 404
- A Razorpay order's notes name what it pays for: `intent_id`, `booking_id`, or `charge_id` (with its `booking_id`). The webhook checks `charge_id` first, then a bill by `gateway_order_id` (a payment can arrive without its order's notes)
