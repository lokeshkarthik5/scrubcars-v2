# Detlio native apps: parity checklist

Generated 1 Nov 2026 from origin/main commit ffbeb7c3 (worktree `~/Desktop/Detlio-Dev/open-prs/detlio-native-signin`). Source of truth: `apps/users` (41 `page.tsx` routes) and `apps/vendors` (22 `page.tsx` routes). Compared with `docs/mobile-migration.md`. Read-only pass: nothing was run on a device or against a live API.

How to read it: `Done` is for ticking off. `Plan version` is the version in `docs/mobile-migration.md` that lists the feature (v0, v1.0, v1.1, v1.2). `**not in plan**` means the plan does not name it at any version; the bracket is a suggested version. `Native needs` names the native module or API addition. Where a row says "(owner addition)" the owner has required it in customer v1.0 even though the plan puts it elsewhere or omits it. Rows were written by reading the code, so labels and limits are as of ffbeb7c3; a few shell rows (bottom nav, garage switcher, log out) appear in two garage tables because two readers covered them.

**Counts:** garage app 187 rows (44 not in plan); customer app 262 rows (47 not in plan); 449 in total, 91 not in plan.

**Owner additions to customer v1.0 (marked in the tables):** leave and report reviews, cancel and reschedule, pay for extra work and final bills, receipts. **New rating screens (mockup `ratings.html` frames B to E; web lacks them, the API mostly has them):** tags on the review form, tag counts and histogram on a garage's reviews, garage reply and report in the garage app's reviews, "New on Detlio" and "Known for" chips on list cards. Server support exists (migration 0065): `POST /reviews` accepts `tags`; `GET /reviews/vendors/:id/summary`; `POST /reviews/:id/report`; `GET /vendors/me/reviews`, `PUT /vendors/me/reviews/:id/reply`, `POST /vendors/me/reviews/:id/report` (`apps/server/src/modules/reviews/reviews.routes.ts:28-125`). None of the garage-side three has a client function in `packages/core/src/api` (grep for `me/reviews` finds nothing), and `submitReview` has no `tags` field.

### Cross-cutting notes (garage)

#### Cross-cutting findings (garage jobs)

- Push URLs sent to garages (`apps/server/src/lib/push-messages.ts`): job events use `/bookings?tab=<incoming|upcoming|completed|cancelled>#job-<bookingId>` (new booking and respond-soon and rescheduled-to-pending -> `incoming`; picked time, extra work paid/declined, redo booked, request booked, rescheduled-accepted -> `upcoming`; cancelled/declined/not-accepted-in-time -> `cancelled`); redo-claim messages use `/guarantee#claim-<claimId>`; new visit request uses `/requests`; the notification-prefs link uses `/settings/notifications`. The Bookings page maps `incoming`->New, `upcoming`->Today, `completed`/`cancelled`->Done and the hash redirects non-pending jobs to `/bookings/<id>`. Native deep-link/notification routing must keep all of these.
- Garage push set (all garage templates): new booking (urgent, "accept within N min"), respond-soon (10 min before auto-cancel), customer picked a suggested time, none of the times worked, extra work paid, extra work declined, customer cancelled, booking moved, not accepted in time, redo claim to answer / approved / decided, free redo booked, new visit request, request booked. Pushes carry booking basics only, never customer phone, address or pickup code.
- Polling: jobs list every 10 s while visible (single shared poller, refetch on becoming visible); `useNow` ticks every 10 s for countdowns and list grouping; garage open/closed re-evaluated every 60 s (hours cached 5 min); requests count every 30 s; push-device state reloaded on garage switch only; no websockets or SSE.
- Offline handling: none. Service worker has no cache and no fetch handler. Failed list read shows LoadError with Retry only when no earlier list exists; otherwise last list stays. Mutations toast the server message and re-read.
- Undo queue: browser `sessionStorage` + `keepalive` + `beforeunload` prompt are web-only mechanisms; native needs AppState-based flush and a decision on what happens if the app is killed during the 5 s wait (not confirmed).
- Money gating: operator seat never sees prices on the new-booking card, This week tile, extra-work total, final bill totals; owner seat sees them. Role comes from `useIsVendorAdmin()`; the server is the real boundary. Pause/resume, Services, Earnings, Settings, Photos are owner-only.
- Time zone: all day grouping (Today, Tomorrow, Later, day chips) uses IST regardless of device time zone.
- Photo privacy: job photos live in the private bucket and are only seen through 15 min presigned URLs; every upload path re-encodes to JPEG (1600 px, q 0.85) which strips EXIF/GPS; garage listing photos and logo use `stripImageMetadata` (max edge 2560, JPEG/PNG/WebP) before the public PUT.
- Codes: pickup and delivery codes are typed by the garage from the customer's words; the picked-up code is held in memory only, never stored in the Undo queue storage, and the server never sends codes to the garage.
- Request headers: every garage call carries `X-Vendor-Id`; Undo steps capture the vendor id at press time so a garage switch cannot redirect them.
- Not in the scoped files but linked from them (need own rows in other parts): /earnings, /reviews, /requests, /guarantee, /agreement, /account, /settings (and ?tab=location, ?tab=time-off), /settings/notifications.

#### Cross-cutting findings (garage business)

- Seat model: `role` is `vendor_admin` (owner or admin, `isOwner` marks the owner) or `vendor_operator`. Operators see only Home and Bookings (plus `/account` and `/settings/notifications`); `/earnings`, `/services`, `/settings*`, `/agreement`, `/guarantee` redirect them to `/home`. Native must hide the same tabs and still handle a 403 gracefully (hiding is not the boundary).
- Owner has no "Delete my account" on web: the owner sees only "Close my garage" (a request Detlio acts on by phone). Non-owners get "Leave this garage" and "Delete my account". Plan v1.0 says "delete my account / leave garage"; check whether the owner path meets Apple's in-app account-deletion rule.
- Reviews: the portal shows replies read-only; `PUT /vendors/me/reviews/:reviewId/reply` exists (AGENTS.md: 24 h edit window, owner seat only) but no web UI, so the native "reply" is new UI. `/reviews` is not in the bottom nav and not linked from the files read here (not confirmed how it is reached; `/reviews` has no operator redirect).
- Uploads: all use presigned R2 PUT (`stripImageMetadata` strips EXIF on web for service photos, garage photos, logo and document images; PDFs are sent untouched). Native replacement is `expo-image-manipulator`. Service video goes to Cloudflare Stream (basic POST up to 200 MB, tus above) with 60 s / 2 GB limits and 4 s status polling; the privacy-consent tick is mandatory before any service media upload (`consent: true` sent to the API).
- Document viewing uses 5-minute signed links opened in a new tab; native should open them with the system/in-app browser without persisting the URL.
- Maps: the same `LocationPicker` (search, tap/drag, GPS, Google-link paste with warnings) is used in onboarding step 2 and Settings > Location; `CoverageEditor` polygon drawing is separate. Needs one native map solution for both.
- Date and time inputs (working hours, holidays, earnings custom range, document expiry) use browser pickers; native needs date/time pickers with min/max.
- CSV export (earnings) is a Blob download; native must write a file and open the share sheet.
- Agreement PDF opens in a new tab; native needs an in-app PDF viewer or share/open-in.
- Web Push UI (`PushDeviceCard`, `usePushDevice`) is browser-specific (service worker, iOS add-to-home-screen); native replaces it with OS permission + device-token registration, while keeping the same screen text where it still applies.
- Deep-link anchors used on web: `/requests#request-:id`, `/guarantee#claim-:id`; native push taps should open the matching card.
- Support session (admin impersonation): `AccountActions` hides itself and reviews reply returns 403; native does not need an admin-impersonation mode.
- Onboarding creates the garage at step 2 (`POST /vendors`), so a user who quits after step 2 already exists as a vendor with no hours or services; the route gate allows steps 3-4 for that state and native must do the same.
- Store/state: `sessionStorage` (`auth_phone`, `auth_purpose`, expiry/resend timestamps, `auth_next`) holds the OTP hand-off between login and verify; native should use navigation params or in-memory state.

#### Cross-cutting findings (customer booking)

Native map choice is open: maplibre-react-native for parity, or react-native-maps with keys.
- Payment code lives in `@repo/core` (`razorpay.ts`, `payment-confirmation.ts`) with the browser script only inside `openRazorpayCheckout`. Native swaps only that function for the Razorpay SDK; create-order, verify, retry (1 s, 3 s, 6 s) and 60 s poll every 3 s stay the same. Three flows use it: new booking (`/booking-intents`), pay unpaid booking (`/payments/orders`), bill or extra work (`/bookings/:id/charges/:chargeId/pay`).
- Booking detail polls every 5 s (open) or 15 s (closed but bill may change); native should pause polling in background and refresh on foreground/push.
- Local persistence on web uses localStorage: location store, booking draft (`detlio:booking-draft`, 24 h), pending checkout (24 h), tip hidden date, sessionStorage OTP clocks and garage-seen flag. All map to AsyncStorage (none are secrets).

- Ratings: server already supports tags, summary, `knownFor`, garage reply and report (migration 0065); only the apps' UI is missing. `submitReview` in core needs a `tags` field. Vendor web also lacks reply and report forms.
- Meta Pixel and Conversions API calls (`trackPurchase`, `trackRegistration`) are web-only per plan; native sends first-party `POST /events` only.
- No Google OAuth button in customer web, and no calendar add, share or copy-reference on booking detail.
- Not confirmed: the server route for customer car photo presign (assumed `POST /bookings/:id/photos/upload-url` from the shared helper); whether Google sign-in is still live on the server.
